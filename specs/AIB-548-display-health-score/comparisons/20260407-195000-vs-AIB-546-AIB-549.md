## Implementation Choices Analysis

### [Spec] Accessible text alternative for score state
| Ticket | Approach |
|--------|----------|
| AIB-548 | `aria-label="Project health score: 81, Good"` — includes band label |
| AIB-546 | `aria-label="Health score: 85"` — score only |
| AIB-549 | `aria-label="Health score: 85"` — score only |

**Best**: AIB-548 - Richer label includes score band for screen readers.

### Decision Point 1: Server-side vs Client-side Score Computation
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-548 | Server-side: `getUserProjectsWithHealthSummary()` computes globalScore, label, color tokens | Yes - single source of truth | Pre-computed data, no client logic |
| AIB-546 | Client-side: passes raw healthScore, client calls `getScoreColorConfig()` | Acceptable | Simpler server, duplicated logic |
| AIB-549 | Client-side: passes raw healthScore, client calls `getScoreColor()` | Acceptable | Simpler server, duplicated logic |

**Best**: AIB-548 - Server-side computation means the API response is the canonical source for how scores are displayed. Prevents client/server drift.

### Decision Point 2: Quality Gate Data Source
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-548 | Computes average from Job table (30-day rolling, SHIP tickets) via `getQualityGateAveragesByProjectId()` | Yes - uses actual verify data | More accurate, dynamic, extra query |
| AIB-546 | Uses `qualityGate` field from HealthScore table directly | Acceptable | Simpler, but depends on HealthScore being current |
| AIB-549 | Uses `qualityGate` field from HealthScore table directly | Acceptable | Same as AIB-546 |

**Best**: AIB-548 - The quality gate score derived from actual verify jobs is more accurate and doesn't depend on stale HealthScore data.

### Decision Point 3: Heart Visual Design
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-548 | Pill badge with lucide Heart icon + text. Uses Tailwind tokens from `getScoreColor()` | Yes - uses existing utilities, Tailwind tokens | Consistent with shadcn patterns |
| AIB-546 | Custom SVG heart with embedded `<text>`. Uses `hsl()` CSS values | Warning - `hsl()` strings are hardcoded CSS values | Custom look, but bypasses Tailwind purger |
| AIB-549 | Custom SVG heart with Tailwind fill classes (`fill-ctp-green`, etc.) | Yes - uses Tailwind tokens | Custom look with proper tokens |

**Best**: AIB-548 - Pill badge is more aligned with shadcn/ui component patterns per constitution II. AIB-549 is acceptable. AIB-546's `hsl()` values are borderline hardcoded colors.

### Decision Point 4: Test Strategy
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-548 | Extends existing `crud.test.ts` + new `project-card.test.tsx` | Yes - "extend, don't duplicate" | Follows constitution exactly |

| AIB-549 | Unit test only, no integration test | Warning - no API verification | Missing server-side coverage |

**Best**: AIB-548 - Constitution III explicitly says "extend, don't duplicate" and AIB-548 extends the existing crud.test.ts.

### Decision Point 5: Code Organization
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|

## Ranking & Recommendation

### 1. **AIB-548** - Best code (score: 94%)
**Why it wins**:
- Server-side score computation provides single source of truth
- Quality gate derived from actual Job data (30-day rolling)
- Rich TypeScript type system (`ProjectHealthLabel`, `ProjectHealthSubScores`, `ProjectHealthSummary`)
- Extends existing test file per constitution ("extend, don't duplicate")
- Pill badge design aligns with shadcn/ui patterns
- Richer accessibility labels include score band name

### 2. **AIB-546** - (score: 85%)
**Why it lost**:
- Client-side color computation duplicates server capability
- Uses `hsl()` CSS values instead of Tailwind tokens (borderline CLAUDE.md color rule)
- Hover-controlled popover adds unnecessary `useState` complexity
- Creates new test files rather than extending existing ones

### 3. **AIB-549** - (score: 82%)
**Why it lost**:
- No integration test to verify API response shape
- Creates `transforms/` directory for a single function (premature abstraction)
- Client-side score computation
- Least test coverage (1 file vs 2 for others)
