## Implementation Choices Analysis

### [Spec] Empty or short batch must not loop
| Ticket | Approach |
|--------|----------|
| AIB-894 | If 0 tickets are added, `shipTotal` is reconciled to the loaded count, so `hasMore` becomes false |
| AIB-890 | `exhaustedAtTotal` state turns `hasMore` off until the server total changes |
| AIB-891 | No guard: the `isLoadingMore` toggle re-runs the effect while the sentinel is still visible, so it fetches the same offset again |
| AIB-892 | No guard: the observer is recreated on `isLoadingMore` change and fires again, so the request repeats in a loop |

**Best**: AIB-894 / AIB-890. They are the only ones that handle the spec edge case where the "counter says more but the batch is empty".

### [Spec] Polling keeps loaded SHIP tickets
| Ticket | Approach |
|--------|----------|
| AIB-894 | Refetch sends `?shipLimit=max(50, loaded)` (Zod-capped at 1000), so the server returns fresh data for every loaded ticket |
| AIB-890 | Client merge keeps previously loaded SHIP tickets absent from the refresh, so those tickets stay stale until the next scroll |
| AIB-891 | Same client merge as AIB-890 (stale retained tickets) |
| AIB-892 | `shipLimit` refetch like AIB-894 (cap 500), but uses a magic number instead of a shared constant |

**Best**: AIB-894. The server is the source of truth, and the constants are shared between the API, DB and hook.

### [Spec] Drag & drop safety
| Ticket | Approach |
|--------|----------|
| AIB-894 | `paused: isDragging` passed through `shipInfiniteScroll` |
| AIB-890 | `isLoadPaused: isDragging` |
| AIB-891 | `isLoadMorePaused: isDragging` |
| AIB-892 | No pause, so batches can load in the middle of a drag |

**Best**: AIB-894 (tied with AIB-890 and AIB-891).

### Decision Point 1: Component structure
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-894 | New `ShipInfiniteScrollFooter` + single `shipInfiniteScroll` prop object | Yes (II) | Isolated and testable; StageColumn shrinks |
| AIB-890 | Inline in StageColumn, reuses the existing `useIntersectionObserver` hook, 5 new props | Yes | Good reuse, but StageColumn grows |
| AIB-891 | Inline observer plus a layout re-check via `getBoundingClientRect` | Yes | Robust, but StageColumn grows |
| AIB-892 | Inline observer with `rootMargin: 100%` | Yes | Minimal; no pause or loop guard |

### Decision Point 2: Load state management
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-894 | `useMutation` + ref guard; offset read from the cache at call time | Yes (TanStack) | Simple, no stale offset |
| AIB-890 | Hand-rolled async state machine (useState + 6 refs) instead of useMutation | Partial | Works, but a lot of complexity |
| AIB-891 | `useMutation` + ref guard; offset comes from the render closure | Yes | Simple |
| AIB-892 | `useMutation` + ref guard + `reset()` on every load | Yes | Simple |

### Decision Point 3: Pagination correctness
Only AIB-894 adds an `id` tie-breaker to the SHIP `orderBy` in all 3 queries. Without it, offset pages can overlap or skip tickets when `updatedAt` values are equal.

## Ranking & Recommendation

### 1. **AIB-894** - Best code (score: 93%)
**Why it wins**:
- Complete spec fulfillment, including the empty-batch loop guard, drag pause and accessibility
- Server-driven refetch depth plus deterministic ordering, with shared constants in `lib/tickets/ship-pagination.ts`
- Clean extracted footer component and a single prop object

### 2. **AIB-890** (score: 89%)
**Why it lost**: Over-engineered hook (6 refs, manual state instead of useMutation). The client-side merge keeps stale SHIP tickets after polling.

### 3. **AIB-891** (score: 78%)
**Why it lost**: No loop guard on empty batches, a stale client merge, and only unit tests.

### 4. **AIB-892** (score: 74%)
**Why it lost**: No drag pause, no empty-batch loop guard, and magic-number limits.
