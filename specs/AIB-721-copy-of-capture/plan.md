# Implementation Plan: Capture and Display Agent Execution Logs

**Branch**: `AIB-721-copy-of-capture` | **Date**: 2026-04-23 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `specs/AIB-721-copy-of-capture/spec.md`

## Summary

Capture agent execution output (Claude Code, Codex, Mistral/vibe, Gemini) when jobs reach terminal state, normalize it to a common structured format, and display it in the ai-board timeline UI with inline previews and a detailed log viewer. Logs are stored in a separate `JobLog` table to avoid bloating job queries, retained for 30 days, and automatically pruned after expiry.

## Technical Context

**Language/Version**: TypeScript 5.9 (strict), Node.js 22.20.0
**Primary Dependencies**: Next.js 16 (App Router), React 18, Prisma 6.x, TanStack Query v5, shadcn/ui, Zod
**Storage**: PostgreSQL 14+ (Prisma ORM). New `JobLog` table for full log content; `Job` model extended with `logStatus` + `logSummary`.
**Testing**: Vitest (unit + integration), Playwright (E2E browser tests)
**Target Platform**: Web application (Linux server + browser client)
**Project Type**: Web application (Next.js App Router)
**Performance Goals**: Log available within 60s of job completion (SC-001); job list page load time increase <10% (SC-005)
**Constraints**: Max 5MB per log payload; 30-day retention; log capture must not interfere with existing telemetry (FR-011, FR-015)
**Scale/Scope**: 4 agent types, all workflow types (speckit, quick-impl, verify, iterate)

## Implementation Phases

### Phase 1: Data Layer (Database + Types)

**Goal**: Schema migration, type definitions, Prisma client generation.

1. Add `LogStatus` enum and `JobLog` model to `prisma/schema.prisma` (see [data-model.md](data-model.md))
2. Add `logStatus`, `logSummary`, and `jobLog` relation to `Job` model
3. Drop unused `logs` column from `Job`
4. Run `bunx prisma migrate dev` to generate migration
5. Create `lib/logs/types.ts` with `NormalizedLogEntry`, `LogEventType`, `LogUploadPayload`, `JobLogResponse`
6. Update `lib/types/job-types.ts` — add `logStatus` and `logSummary` to `TicketJobWithTelemetry`

**Depends on**: Nothing
**Validates**: Schema compiles, `bun run type-check` passes

### Phase 2: Log Processing (Parsers + Summarizer + Truncator)

**Goal**: Server-side logic for normalizing, summarizing, and truncating agent output.

1. Create `lib/logs/log-parser.ts`:
   - `parseAgentOutput(rawOutput: string, agentType: string): NormalizedLogEntry[]`
   - Agent-specific parsing functions: `parseClaudeOutput`, `parseCodexOutput`, `parseMistralOutput`, `parseGeminiOutput`
   - Fallback: if parsing fails for an agent type, return a single `message` entry with the raw content (FR-015 resilience)
2. Create `lib/logs/log-summarizer.ts`:
   - `generateLogSummary(entries: NormalizedLogEntry[], jobStatus: string): string`
   - For FAILED jobs: extract error entries, return last error + entry count
   - For COMPLETED jobs: count tool invocations, return key milestones + completion message
   - For CANCELLED jobs: return "Cancelled after N entries" + last entry content
   - Max summary length: 2,000 characters
3. Create `lib/logs/log-truncator.ts`:
   - `truncateOutput(rawOutput: string, maxBytes: number): { content: string; truncated: boolean }`
   - Preserve first 25% + last 25% of maxBytes, insert `\n\n--- [TRUNCATED: original size X bytes] ---\n\n` marker (FR-013)
4. Write unit tests: `tests/unit/log-parser.test.ts`, `tests/unit/log-summarizer.test.ts`, `tests/unit/log-truncator.test.ts`

**Depends on**: Phase 1 (types)
**Validates**: All unit tests pass

### Phase 3: API Endpoints

**Goal**: Log upload (POST) and retrieval (GET) endpoints per [contracts/job-logs-api.md](contracts/job-logs-api.md).

1. Create `app/api/jobs/[id]/logs/route.ts`:
   - **POST handler** (workflow auth):
     - Validate auth via `validateWorkflowAuth(request)` — follows pattern from `app/api/jobs/[id]/status/route.ts:57-64`
     - Validate body with Zod schema (`agentType` enum, `rawOutput` string max 5MB)
     - Verify job exists
     - Check for existing `JobLog` (return 200 if exists — idempotent)
     - Parse raw output → `NormalizedLogEntry[]` using `parseAgentOutput()`
     - Generate summary using `generateLogSummary()`
     - Truncate raw output if needed using `truncateOutput()`
     - Create `JobLog` + update `Job.logStatus`/`Job.logSummary` in a Prisma transaction (constitution V: transactions for multi-table ops)
     - Return 201 with metadata
   - **GET handler** (session auth):
     - Require auth via `requireAuth()`
     - Look up job, verify project access via `verifyProjectAccess()` (FR-008)
     - Check `logStatus`: NONE → 404, PRUNED → 410, AVAILABLE → fetch `JobLog`
     - Return full log response with entries parsed from JSON
2. Update `app/api/projects/[projectId]/tickets/[id]/timeline/route.ts`:
   - Verify `logSummary` and `logStatus` appear in the response (no code change needed if `findMany` returns all fields)
3. Update `app/api/projects/[projectId]/tickets/[id]/jobs/route.ts`:
   - Add `logStatus` to the select clause (line ~131)
4. Write integration tests: `tests/integration/jobs/job-logs.test.ts`
5. Extend `tests/integration/tickets/timeline.test.ts` — verify `logStatus` and `logSummary` in timeline response
6. Extend `tests/integration/jobs/ticket-jobs.test.ts` — verify `logStatus` in response

**Depends on**: Phase 2 (parsers)
**Validates**: Integration tests pass, `bun run type-check` passes

### Phase 4: Workflow Changes (Capture + Upload)

**Goal**: Capture agent output in all workflows and upload to the log endpoint.

1. Modify `.github/scripts/run-agent.sh`:
   - Define `LOG_CAPTURE_FILE` pointing to `/tmp/agent-output-$$.log`
   - In each `invoke_*` function, pipe output through `tee "$LOG_CAPTURE_FILE"`:
     - Claude: `claude ... 2>&1 | tee "$LOG_CAPTURE_FILE"`
     - Codex: `echo "$prompt" | codex exec ... 2>&1 | tee "$LOG_CAPTURE_FILE"`
     - Mistral: `vibe ... 2>&1 | tee "$LOG_CAPTURE_FILE"`
     - Gemini: `gemini ... 2>&1 | tee "$LOG_CAPTURE_FILE"`
   - Export `LOG_CAPTURE_FILE` for the workflow to use in subsequent steps
   - Preserve exit codes via `pipefail` (already set at line 2)
2. Create `.github/scripts/upload-agent-logs.sh`:
   - Reads `LOG_CAPTURE_FILE`, validates it exists and is non-empty
   - Reads `AGENT_TYPE` from env (or `$1`)
   - POSTs to `${APP_URL}/api/jobs/${JOB_ID}/logs` with `WORKFLOW_API_TOKEN` auth
   - Uses `jq` to JSON-encode the raw output safely (handles special characters)
   - Handles failure gracefully: log warning, exit 0 (FR-015 — never block status update)
3. Add "Upload Agent Logs" step to all 4 workflows:
   - `speckit.yml` — after "Execute Spec-Kit Command" step, before "Update Job Status" steps
   - `quick-impl.yml` — after agent execution, before status update
   - `verify.yml` — after agent execution, before status update
   - `iterate.yml` — after agent execution, before status update
   - Step runs with `if: always()` to capture logs on failure/cancellation too
   - Failure is non-blocking: `run: ... || echo "Log upload failed (non-blocking)"`

**Depends on**: Phase 3 (API endpoint to receive uploads)
**Validates**: Manual workflow test — verify log appears in database after job completes

### Phase 5: UI — Timeline Integration

**Goal**: Display log previews in the timeline and provide a "View full logs" action.

1. Create `components/logs/log-preview.tsx`:
   - Renders condensed log summary inline below job event text
   - Shows error text in `text-red-500` for FAILED jobs
   - Shows milestone summary in `text-muted-foreground` for COMPLETED jobs
   - Shows "Logs expired" message with `text-subtext0` for PRUNED status
   - Hidden for NONE status (FR-014)
   - No hardcoded hex colors — uses Tailwind semantic tokens (per CLAUDE.md color rules)
2. Modify `components/timeline/job-event-timeline-item.tsx`:
   - For completion events (`eventType === 'complete'`), render `<LogPreview>` below the status line
   - Add "View full logs" button (shadcn `Button` variant="link" size="sm") when `logStatus === 'AVAILABLE'`
   - Button opens the `LogViewer` dialog
   - Follows existing pattern: content inside `<TimelineContent>` wrapper
3. Create `app/lib/hooks/queries/use-job-logs.ts`:
   - `useJobLogs(jobId: number, enabled: boolean)` — TanStack Query hook
   - Fetches from `GET /api/jobs/${jobId}/logs`
   - `enabled` controls lazy loading (only fetch when dialog opens)
   - No polling (logs are immutable once written)
4. Create `components/logs/log-viewer.tsx`:
   - shadcn `Dialog` with `aurora-dialog-overlay` styling (per aurora B+ theme convention)
   - Header: job command display name (using `getJobDisplayName()`), agent type badge, timestamp
   - Body: scrollable list of log entries
   - Loading state with skeleton
   - Error/pruned/empty state handling (FR-014)
   - Truncation indicator banner if `truncated === true` (FR-013)
5. Create `components/logs/log-entry-row.tsx`:
   - Individual log entry with:
     - Timestamp (relative format using same pattern as `formatRelativeTime` from timeline item)
     - Event type icon (lucide-react: MessageSquare for message, Wrench for tool_invocation, AlertCircle for error, ArrowRight for status_change)
     - Content text with `font-mono text-sm` for code/error content
   - Color-coded by event type using Tailwind palette classes
6. Write component tests: `tests/unit/components/log-preview.test.tsx`, `tests/unit/components/log-viewer.test.tsx`

**Depends on**: Phase 3 (API endpoints for data), Phase 1 (Job model fields for timeline)
**Validates**: Component tests pass. Manual browser testing: view timeline with log preview, open full log viewer.

### Phase 6: Log Pruning

**Goal**: Automated cleanup of expired logs per FR-009/FR-010.

1. Create `lib/logs/prune-expired-logs.ts`:
   - `pruneExpiredLogs(retentionDays: number): Promise<{ pruned: number; errors: number }>`
   - Find `JobLog` records where associated job's `completedAt` < now - retentionDays
   - Delete in batches of 100 (avoid long-running transactions — constitution V)
   - For each deleted `JobLog`, update `Job.logStatus = PRUNED`, `Job.logSummary = null`
2. Create `app/api/cron/prune-logs/route.ts`:
   - POST handler with CRON secret auth
   - Calls `pruneExpiredLogs(30)`
   - Returns summary JSON
3. Write integration test: extend `tests/integration/jobs/job-logs.test.ts` with pruning scenarios

**Depends on**: Phase 1 (data model), Phase 3 (logs exist to prune)
**Validates**: Integration tests pass — logs older than threshold are pruned, job metadata preserved

## Complexity Tracking

No constitution violations. All gates pass.

| Concern | Mitigation |
|---------|-----------|
| 5MB log payload in HTTP request | Validated server-side by Zod schema. Workflows use `curl --max-time 30` for upload timeout. |
| Agent output parsing reliability | Fallback: if parser fails, store raw content as a single `message` entry. Parsing never blocks storage. |
| Timeline query performance with new fields | `logSummary` is TEXT on Job (not JOIN). `logStatus` is an enum column with minimal overhead. Full log content in separate table — never fetched by timeline. |
| Pruning under load | Batched deletes (100 per batch). CRON runs at low-traffic time. Idempotent — safe to retry. |
