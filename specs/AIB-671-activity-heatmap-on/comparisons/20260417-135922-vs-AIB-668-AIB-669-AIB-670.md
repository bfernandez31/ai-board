## Implementation Choices Analysis

### Decision Point 1: Component Decomposition
| Ticket | Approach |
|--------|----------|
| AIB-671 | Single `activity-heatmap.tsx` (~363 lines, all logic inline) |
| AIB-668 | Single `activity-heatmap.tsx` (~395 lines) |
| AIB-669 | **Split into 3 files**: `activity-heatmap.tsx` (orchestrator), `heatmap-filters.tsx`, `heatmap-grid.tsx` |
| AIB-670 | Single `activity-heatmap.tsx` (~344 lines) |

**Best**: **AIB-669** — aligns with Constitution II (Component-Driven: small, focused components).

### Decision Point 2: Query/Aggregation Location
| Ticket | Approach |
|--------|----------|
| AIB-671 | `lib/activity-heatmap/{period,queries,types}.ts` — clean domain split |
| AIB-668 | `lib/activity-heatmap/{aggregations,queries,types}.ts` + `app/globals.css` tweaks |
| AIB-669 | `lib/activity-heatmap/{aggregations,queries,types}.ts` — shared between server/client |
| AIB-670 | `lib/analytics/{activity-heatmap,activity-heatmap-grid}.ts` — bundles under analytics (unrelated domain) |

**Best**: **AIB-669 / AIB-671 / AIB-668** — all place code in a dedicated `activity-heatmap` folder. AIB-670's placement under `lib/analytics/` is misleading (analytics dashboard is a separate feature).

### Decision Point 3: Test Strategy
| Ticket | Tests |
|--------|-------|
| AIB-671 | Integration (route) + unit (period) — no component test |
| AIB-668 | Integration + unit (aggregations) + component |
| AIB-669 | Unit (aggregations) + component — no integration |
| AIB-670 | 2 unit + integration + component (most breadth) |

**Best**: **AIB-670** for breadth; **AIB-668** for balance (has integration + component). **AIB-669** lacks integration test for API route.

### Decision Point 4: API Route Naming
| Ticket | Path |
|--------|------|
| AIB-671 | `/api/activity-heatmap` |
| AIB-668 | `/api/user/activity-heatmap` |
| AIB-669 | `/api/activity-heatmap` |
| AIB-670 | `/api/user/activity` (generic, ambiguous) |

**Best**: AIB-671 / AIB-669 — clearest feature-scoped route.

## Ranking & Recommendation

### 1. **AIB-669** — Best code (92%)
**Why it wins**:
- Only implementation that splits the UI into focused sub-components (filters + grid + orchestrator), following Constitution II.
- Clean `lib/activity-heatmap/` domain folder.
- Strong unit + component test coverage.
- Feature-scoped API route path.

### 2. **AIB-670** — 90%
**Why it lost**:
- Best test breadth (4 files), but puts shared code under `lib/analytics/` (wrong domain).
- Ambiguous `/api/user/activity` route name.
- Monolithic 344-line component.

### 3. **AIB-668** — 90%
**Why it lost**:
- Good balance of tests (integ + unit + component) but the largest single-file UI (395 lines).
- Adds `globals.css` tweaks rather than relying fully on Tailwind utilities.

### 4. **AIB-671** (source) — 88%
**Why it lost**:
- Monolithic 363-line UI component.
- No component-level test (only integration + unit-period).
- Functionally equivalent on spec fulfillment, but least modular and least tested at the UI layer.
