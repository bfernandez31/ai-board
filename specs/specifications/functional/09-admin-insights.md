# Admin Insights - Functional Specification

## Purpose

The Admin Insights page provides operators with a platform-wide vantage point on what Claude Code agents are doing across every project. It hosts a manually triggered, archived series of reports generated by Claude Code's built-in `/insights` analyzer, surfacing usage patterns, recurring frictions, big wins, and suggested CLAUDE.md additions synthesized from the raw native Claude Code session JSONL artifacts captured for every Claude job.

It is the main filled section of the admin shell — a thin chrome (global header + left sidebar) that wraps every `/admin/*` page and is sized to host additional admin sections over time.

## Accessing the Admin Area

The admin area lives at `/admin` and is accessible only to operators whose authenticated email appears in the platform's admin allowlist. `/admin/insights` is the section dedicated to platform-wide Claude Code insights and is reached either from the sidebar or by typing the URL directly.

### Discreet Entry Point for Admins

Allowlisted admins see an **"Admin"** entry inside the user-avatar dropdown (desktop) and inside the mobile hamburger menu, in both cases placed between the existing account settings and the sign-out action and visually separated from them. Clicking it navigates to `/admin`.

The entry is **server-gated**: the next-auth session callback computes `session.user.isAdmin` from the same allowlist used by the page guard, on every session resolution, so allowlist rotations take effect on the operator's next request without requiring a re-login. Non-admin sessions never receive the field set to `true` and the menu item is omitted from the rendered markup entirely — non-admins receive no DOM node, no badge, no hint of the admin area's existence.

### Admin Shell Layout

The admin shell wraps every `/admin/*` page with:

- The global application header (logo, notification bell, user avatar) — unchanged from the rest of the application
- A left navigation sidebar labelled **"Espace admin"** containing a vertical, extensible list of admin sections
- A main content area filling the remaining width with consistent padding

The sidebar items in the current build:

| Item | Path | Active-state match |
|------|------|--------------------|
| **Accueil** | `/admin` | exact (`/admin` only) |
| **Insights LLM** | `/admin/insights` | prefix (`/admin/insights` and any descendant) |

Each item is an icon + label pair. The active item carries `aria-current="page"`, an accent background, and a left-edge accent rail.

Below the section list, separated by a divider, the sidebar ends with a **"Retour à l'app"** link that navigates back to `/` and lets the operator leave the admin shell without using the browser back button.

### Access Control

Every admin route — page, API endpoint, asset path, report-body endpoint — applies the same gate. Any request not made by an allowlisted user returns a **Not Found** response byte-equivalent to a genuinely missing path (matching status code, body bytes, and headers). This includes:

- Unauthenticated requests
- Authenticated users whose email is not in the allowlist

The response intentionally cannot be distinguished from `/this-path-does-not-exist`. No JSON error body, no descriptive message, no `Forbidden` status, nothing that would let a probe confirm the admin area exists.

The allowlist is managed via deployment configuration (a single environment variable) rather than a database role or runtime UI. Adding or removing an operator requires a configuration change and is reflected on the operator's next request — no application restart, schema migration, or cache flush is needed.

## The Insights Page

`/admin/insights` is a single page that presents:

1. The **latest COMPLETED report** rendered inline
2. A **metadata header** describing the report's scope
3. A **past-reports list** (reverse-chronological) for switching between reports
4. A **"Run new analysis"** action to trigger a new run

### Latest Report Rendering

When at least one COMPLETED report exists, the page renders the most recent COMPLETED report's HTML body inline inside a sandboxed iframe. The iframe loads from a dedicated authenticated endpoint and executes the report's scripts and charts (which the `/insights` analyzer needs for its interactive content) while remaining isolated from the host application's cookies, storage, and DOM.

### Metadata Header

Each rendered report displays a metadata header in the exact canonical form:

> Analyzed **N** Claude Code sessions across **M** tickets shipped between **START_DATE** and **END_DATE**.

The header also displays the report's generated timestamp. `N` and `M` are derived from the same enumeration the workflow used as analysis input, so the header and report content never drift.

### Empty State

When no COMPLETED report has ever been produced, the page displays a clear empty state explaining that no analysis has been run yet, alongside the "Run new analysis" action (subject to the pre-flight check below).

### Running State

When a report is currently RUNNING:
- The page shows a "Running since RUN_START_DATE" placeholder
- The "Run new analysis" button is disabled
- The page polls for status changes every 15 seconds and updates automatically when the run reaches a terminal state

## Triggering a New Analysis

Clicking "Run new analysis" attempts to dispatch a new run. The request passes through two gates:

### Pre-flight Gate (shipped-tickets check)

The system counts tickets that have transitioned to the SHIP stage since the previous successful run's analyzed period end. If that count is zero, the trigger is refused.

**Refusal message** — `"No new shipped tickets since last run on PREVIOUS_RUN_DATE"` (or `"No shipped Claude tickets to analyze yet"` when no successful run has ever produced a report and no Claude jobs exist anywhere).

The pre-flight count uses the same predicate as the workflow's analysis-input enumeration: a Claude job is one whose **effective agent** is Claude — the ticket-level `agent` if set, otherwise the project-level `defaultAgent`. Sessions from non-Claude agents (Codex, Mistral, Gemini) never appear in the count or in the analysis input.

### Concurrency Gate (single-flight)

If a RUNNING report already exists, the trigger is refused with `"Already running since RUN_START_DATE"`. Only one analysis can be in-flight at a time.

### On Acceptance

When both gates pass, the system:
1. Creates a report record in RUNNING status (before dispatching the workflow, so failures still leave an auditable row)
2. Dispatches the analysis job
3. Returns to the page, which now shows the "Running…" state with the button disabled

When the job completes successfully, the new COMPLETED report becomes the latest and renders inline. When the job fails, the report row transitions to FAILED with a non-secret, operator-actionable error reason; the previous COMPLETED report remains the "latest viewable" report, the failure reason is shown on the page, and the trigger button re-enables.

### Period Semantics

- **First-ever successful run**: period starts at the earliest available Claude Code session timestamp and ends at the trigger timestamp.
- **Each subsequent run**: period starts at the previous successful run's period end and ends at the trigger timestamp.

A FAILED run does **not** advance the high-water mark — the next attempt re-covers the same window. Consecutive successful reports cover non-overlapping, gap-free windows.

## Past Reports List

The page displays past reports in reverse-chronological order (newest first). Each entry shows:

- Date generated
- Period covered (start → end)
- Sessions count and tickets count
- Run status (COMPLETED, FAILED, or RUNNING)

The list is capped at 200 entries server-side regardless of how many reports exist in storage. There is no pagination UI, no filter, no search, and no custom date-range selector.

### Selecting Entries

- **COMPLETED entry**: switches the rendered HTML and metadata header to that report. The latest report remains in the list and can be reselected.
- **FAILED entry**: replaces the HTML body with the failure reason; the metadata header still displays the period and counts.
- **RUNNING entry**: shows the "Running…" placeholder.

## Reports Are Read-Only

Reports cannot be edited, annotated, renamed, deleted, or shared via notification from within the application. Once created they persist indefinitely (operators may prune at the storage layer manually if ever needed).

The system never sends notifications (email, push, in-app, webhook) for run start, completion, or failure. Observation is exclusively pull-based via this page.

## Failure & Recovery Behavior

### Stable Failure Surfaces

| Situation | Behavior |
|-----------|----------|
| The analyzer's HTML output is missing the structural markers `/insights` always emits (e.g., "Suggested CLAUDE.md additions", "Big wins", "Horizon") | The run is marked FAILED with reason `"Insights output validation failed"`. A degraded report is never marked COMPLETED. |
| A workflow becomes orphaned (dispatched but never reports a terminal status) and the configured timeout has elapsed | The orphaned RUNNING row is auto-transitioned to FAILED with reason `"Run timed out — workflow did not report terminal status"`. This reconciliation runs lazily on every list-endpoint and trigger-endpoint call. |
| A late workflow callback arrives for a run already auto-FAILED | The callback is a no-op; the terminal status is preserved. |
| A COMPLETED report's stored HTML artifact is no longer retrievable | The page renders a stable placeholder: `"Report content is no longer available."` The metadata header still displays from the database row. |
| A pre-flight check passes but the resulting window contains zero Claude sessions (raw artifacts have aged out) | The analysis still runs; the report header honestly reports zero sessions and the run COMPLETES. |

### Audit Trail

Every accepted trigger leaves exactly one report row in a terminal status (COMPLETED or FAILED). FAILED rows carry a non-secret, operator-actionable error reason that allows an operator to reproduce, retry, or escalate without consulting external logs.

## What Is NOT in This Feature

- No other admin pages (no platform-wide stats dashboard, no user management UI, no project-spanning tools)
- No database-backed admin role system or runtime UI to grant/revoke admin status
- No scheduled, recurring, or event-driven triggers — manual button only
- No analysis of non-Claude agent sessions
- No filtering, search, custom date ranges, or pagination UI on the list
- No editing, annotating, renaming, or deletion of reports
- No notifications for run lifecycle events
- No ticket-level, project-level, or per-user partitioning — this is application-wide by design
