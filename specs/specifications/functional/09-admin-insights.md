# Admin Insights - Functional Specification

## Purpose

The Admin Insights page provides operators with a platform-wide vantage point on what Claude Code agents are doing across every project. It hosts a manually triggered, archived series of reports generated by Claude Code's built-in `/insights` analyzer, surfacing usage patterns, recurring frictions, big wins, and suggested CLAUDE.md additions synthesized from the raw native Claude Code session JSONL artifacts captured for every Claude job.

Each analysis covers **every** Claude agent session of **every** ticket across **all** projects — specify, plan, implement, iterate, verify, and any other Claude session — regardless of the ticket's outcome (shipped, in-progress, failed, abandoned, or rolled back). Sessions are the unit of analysis, not tickets: a multi-session ticket contributes all of its sessions, never just the earliest one. Each session is analyzed exactly once over time, tracked by a durable per-session marker, so consecutive runs neither skip nor double-count sessions at the period boundary.

Insights LLM is one of two pages hosted by the admin shell; the other is the [Admin Home Dashboard](10-admin-home.md) at `/admin`.

## Accessing the Admin Area

The admin area lives under `/admin` and is accessible only to operators whose authenticated email appears in the platform's admin allowlist. `/admin` itself renders the Admin Home Dashboard ([10-admin-home.md](10-admin-home.md)); `/admin/insights` renders this page.

### Entry Point for Admins

Allowlisted operators see an "Admin" entry in the avatar dropdown (and the mobile hamburger menu on small viewports), positioned between "AI Credentials" and the "Sign out" separator. Clicking it navigates to `/admin`. Visibility is decided server-side per render: non-admin viewers receive no Admin entry, no `/admin` href, and no admin-related markup in any response. The entry appears on the next render after an email is added to the allowlist and disappears on the next render after it is removed — no sign-out required.

### Access Control

Every admin route — page, API endpoint, asset path, report-body endpoint — applies the same gate. Any request not made by an allowlisted user returns a **Not Found** response byte-equivalent to a genuinely missing path (matching status code, body bytes, and headers). This includes:

- Unauthenticated requests
- Authenticated users whose email is not in the allowlist

The response intentionally cannot be distinguished from `/this-path-does-not-exist`. No JSON error body, no descriptive message, no `Forbidden` status, nothing that would let a probe confirm the admin area exists.

The allowlist is managed via deployment configuration (a single environment variable) rather than a database role or runtime UI. Adding or removing an operator requires a configuration change and is reflected on the operator's next request — no application restart, schema migration, or cache flush is needed.

## Admin Shell

Every `/admin/*` page renders inside a shared shell composed of:

- The unchanged global application header (logo, notification bell, avatar dropdown) — admin pages do not amputate or replace any header element
- A left sidebar labeled "Espace admin" containing the navigation entries
- A main content area to the right of the sidebar with consistent internal padding across all admin pages

### Sidebar Navigation

V1 navigation entries, each rendered as an icon + label link:

| Entry | Icon | Destination |
|-------|------|-------------|
| Accueil | Home | `/admin` |
| Insights LLM | Sparkles | `/admin/insights` |

A divider sits below the navigation list. Below the divider, a "Retour à l'app" link navigates to `/` (application root) and is visually distinguished from the navigation entries above it.

The sidebar is structured so that additional entries (icon + label + href) or dividers between groups can be added by extending a single data list — no per-item layout change required.

### Active-State Highlighting

Exactly one navigation entry is marked active per route. An entry is active when the current path equals its `href` exactly, or starts with the entry's `href` followed by a `/` segment. The matcher rejects incidental prefix collisions — `/admin/insights-fake` does not activate the Insights LLM entry. The "Accueil" entry (root) is active only on the exact `/admin` path, never on nested admin sections.

The active entry receives both a subtle background tint and a lateral accent indicator on its left edge.

### Theming

All sidebar visuals — typography, colors, hover state, active state, divider, spacing — use the project's existing design tokens. Toggling the application theme updates every shell element in lockstep with the rest of the app.

## The Insights Page

`/admin/insights` is a single page that presents a side-by-side layout:

- A **left pane** (~280 px wide) listing past reports in a compact, dense format
- A **right pane** showing the selected report's content (metadata header, body, and actions)
- A **header row** above both panes with the awaiting-analysis session counter and the "Run new analysis" button

The page does not render its own H1 heading — the admin sidebar's "Insights LLM" label is the sole page identifier.

On screens below the medium breakpoint the two panes stack vertically (past-reports list above, report content below).

### Report Selection

When the page loads, the most recent COMPLETED report is selected by default. If no COMPLETED report exists, the most recent report of any status is selected.

Clicking any report in the left pane updates the right pane to show that report's content without a full page reload. The selected row receives an accent background with a left-edge border indicator, visually distinct from the admin sidebar's own active-state styling.

### Report Rendering (Right Pane)

- **COMPLETED**: The report's HTML body renders inside a sandboxed iframe (`sandbox="allow-scripts"`, no `allow-same-origin`). The iframe loads from a dedicated authenticated endpoint and executes the report's scripts and charts while remaining isolated from the host application's cookies, storage, and DOM.
- **FAILED**: The right pane displays the failure reason text, an optional GitHub Actions link (see [Failed Report Diagnostics](#failed-report-diagnostics)), and a retry button.
- **RUNNING**: A "Run in progress" placeholder with the run start date.

### Metadata Header

Each selected COMPLETED report displays a metadata header in the canonical form:

> Analyzed **N** of **E** Claude Code sessions across **M** tickets

where `N` is the number of sessions actually analyzed, `E` is the number of eligible sessions the run expected to analyze, and `M` is the number of distinct tickets among the analyzed sessions. Below the phrasing the header always shows a scope note — "Covers all Claude sessions across all projects, regardless of ticket outcome." — and a line with the report id and its generated timestamp.

`N` and `E` are derived from the same per-session enumeration the workflow used as analysis input, so the header and report content never drift. When `N` equals `E`, coverage is complete. When `N` is fewer than `E` — eligible sessions whose transcript was pruned before they could be read — a **coverage badge** ("X sessions unavailable") is shown beside the phrasing so the viewer can see that coverage is partial and by how much.

For a RUNNING report the header reads "Analyzing all Claude Code sessions across all projects…"; for any other report whose counts are not yet populated it reads "Counts unavailable for this run." For legacy COMPLETED reports that predate expected-session tracking, the expected count falls back to the analyzed count so the phrasing still reads sensibly and no coverage badge appears.

### Empty State

When no report has ever been produced, the left pane shows "No prior runs" and the right pane displays a placeholder prompting the admin to trigger a first run, alongside the "Run new analysis" action (subject to the pre-flight check below).

### Running State

When a report is currently RUNNING:
- The page shows a "Running since RUN_START_DATE" placeholder in the right pane
- The RUNNING entry appears in the left pane's past-reports list with a status badge
- The "Run new analysis" button is disabled
- The page polls for status changes every 15 seconds and updates both panes automatically when the run reaches a terminal state

## Failed Report Diagnostics

When a FAILED report is selected, the right pane provides diagnostic information and recovery actions:

1. **Error reason**: The failure reason text is displayed in a readable, well-formatted presentation.
2. **GitHub Actions link**: When the failed report's linked job has a recorded workflow run ID, a clickable link opens the corresponding GitHub Actions run page in a new tab. The URL is constructed server-side from the job's `workflowRunId` and the repository coordinates (never exposed as raw environment variables to the client). When no workflow run ID is recorded, the link is simply absent — no broken link is shown.
3. **Retry button**: A "Retry analysis" button triggers a new analysis using the exact same `periodStart` and `periodEnd` from the failed report. The retry goes through the same concurrency gate (ALREADY_RUNNING blocks retry) but skips the eligible-sessions pre-flight check (the original run proved eligibility). On success, a new RUNNING entry appears in the past-reports list. Preflight refusals are displayed to the admin.

## Triggering a New Analysis

Clicking "Run new analysis" attempts to dispatch a new run. The request passes through two gates:

### Pre-flight Gate (eligible-sessions check)

The system counts **eligible Claude sessions that have not yet been analyzed** — completed Claude jobs that belong to a ticket, still have a captured transcript, and carry no per-session "analyzed" marker. If that count is zero, the trigger is refused.

**Refusal message** — `"No new sessions since last run on PREVIOUS_RUN_DATE"` (eligible sessions exist but all are already analyzed) or `"No Claude sessions to analyze yet"` (no eligible Claude sessions exist anywhere and no run has ever completed).

The pre-flight count uses the same predicate as the workflow's analysis-input enumeration: a Claude session is a completed job whose **effective agent** is Claude — the ticket-level `agent` if set, otherwise the project-level `defaultAgent`. The count is **not** gated on ticket SHIP status (sessions from in-progress, failed, abandoned, and rolled-back tickets are all eligible) and is **not** de-duplicated per ticket (every distinct session is counted). Sessions from non-Claude agents (Codex, Mistral, Gemini) never appear in the count or in the analysis input. The awaiting-analysis counter in the page header surfaces this same eligible-session count.

### Concurrency Gate (single-flight)

If a RUNNING report already exists, the trigger is refused with `"Already running since RUN_START_DATE"`. Only one analysis can be in-flight at a time. A session that becomes eligible while an analysis is in flight is not assumed covered by that run — it carries no marker until a run completes, so it remains eligible for the next run.

### On Acceptance

When both gates pass, the system:
1. Creates a report record in RUNNING status (before dispatching the workflow, so failures still leave an auditable row)
2. Dispatches the analysis job
3. Returns to the page, which now shows the "Running…" state with the button disabled

When the job completes successfully, the new COMPLETED report becomes the latest and renders inline. When the job fails, the report row transitions to FAILED with a non-secret, operator-actionable error reason; the previous COMPLETED report remains the "latest viewable" report, the failure reason is shown on the page, and the trigger button re-enables.

### Period Semantics

Which sessions are analyzed is decided by the per-session "analyzed" marker, not by a time window. The period dates are **display-only** context shown on each report:

- **First-ever run**: period starts at the earliest eligible Claude Code session's activity timestamp and ends at the trigger timestamp.
- **Each subsequent run**: period starts at the earliest still-unanalyzed eligible session's activity timestamp and ends at the trigger timestamp.

Coverage is guaranteed by the marker, not the dates: a session is analyzed exactly once because a marker is written for it only when a run COMPLETES, and a marked session is never eligible again. A FAILED run writes **no** markers, so its sessions remain eligible for the next attempt. Consecutive successful runs therefore neither overlap (no session analyzed twice) nor skip any session at the boundary (no session lost).

## Past Reports List

The left pane displays past reports in reverse-chronological order (newest first) as a dense, compact list. Each row is ~30–36 px tall and shows:

- **Generation date** (YYYY-MM-DD)
- **Period window** (compact start → end form, hidden on small screens)
- **Duration** (for COMPLETED reports only — computed from the report's creation timestamp to its completion timestamp, formatted as "Xm Ys"; omitted when the completion timestamp is unavailable)
- **Status badge** (COMPLETED, FAILED, or RUNNING — rendered as a small badge aligned to the right edge of the row)

The list is capped at 200 entries server-side regardless of how many reports exist in storage. There is no pagination UI, no filter, no search, and no custom date-range selector.

### Selecting Entries

Clicking any row in the list selects that report and updates the right pane:

- **COMPLETED entry**: switches the rendered HTML and metadata header to that report.
- **FAILED entry**: shows the failure reason, an optional GitHub Actions link, and a retry button (see [Failed Report Diagnostics](#failed-report-diagnostics)).
- **RUNNING entry**: shows the "Run in progress" placeholder with the run start date.

The selected row is visually highlighted with an accent background and a left-edge border, distinct from the admin sidebar's active-state indicator.

## Reports Are Read-Only

Reports cannot be edited, annotated, renamed, deleted, or shared via notification from within the application. Once created they persist indefinitely (operators may prune at the storage layer manually if ever needed).

The system never sends notifications (email, push, in-app, webhook) for run start, completion, or failure. Observation is exclusively pull-based via this page.

## Failure & Recovery Behavior

### Stable Failure Surfaces

| Situation | Behavior |
|-----------|----------|
| The analyzer's HTML output is missing the structural markers `/insights` always emits (e.g., "Suggested CLAUDE.md additions", "Big wins", "Horizon") | The run is marked FAILED with reason `"Insights output validation failed"`. A degraded report is never marked COMPLETED. |
| A workflow becomes orphaned (dispatched but never reports a terminal status) and the configured timeout has elapsed | The orphaned RUNNING row is auto-transitioned to FAILED with reason `"Run timed out — workflow did not report terminal status"`. This reconciliation runs lazily on every list-endpoint and trigger-endpoint call. |
| A late workflow callback arrives for a run already auto-FAILED | The callback is a no-op; the terminal status is preserved. |
| A COMPLETED report's stored HTML artifact is no longer retrievable | The page renders a stable placeholder: `"Report content is no longer available."` The metadata header still displays from the database row. |
| Some eligible sessions' transcripts are pruned between enumeration and download | Those sessions are skipped (not analyzed, no marker written, still eligible for a later run); the run still COMPLETES on the readable sessions, the report reports analyzed fewer than expected, and the coverage badge signals the gap. |
| Every enumerated session's transcript is pruned before it can be read | The run is marked FAILED with reason `"No readable Claude sessions available"`; no markers are written, so all sessions remain eligible for the next attempt. |

### Audit Trail

Every accepted trigger leaves exactly one report row in a terminal status (COMPLETED or FAILED). FAILED rows carry a non-secret, operator-actionable error reason that allows an operator to reproduce, retry, or escalate without consulting external logs.

## What Is NOT in This Feature

- No user management UI or other admin-section pages beyond Insights LLM and the [Admin Home Dashboard](10-admin-home.md)
- No database-backed admin role system or runtime UI to grant/revoke admin status
- No scheduled, recurring, or event-driven triggers — manual button and retry only
- No analysis of non-Claude agent sessions
- No filtering, search, custom date ranges, or pagination UI on the list
- No editing, annotating, renaming, or deletion of reports
- No notifications for run lifecycle events
- No ticket-level, project-level, or per-user partitioning — this is application-wide by design
