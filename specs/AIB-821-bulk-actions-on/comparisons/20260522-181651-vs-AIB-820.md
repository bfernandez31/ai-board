## Implementation Choices Analysis

### Decision Point 1: Atomicity model
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-821 | All four ops in `prisma.$transaction`; `assertInboxAndProject` precheck throws `BulkConflictError` → full rollback | Yes (V. Database Integrity) | Strict spec compliance; one conflict aborts the batch (intended per spec) |
| AIB-820 | Only `fuseTickets` is transactional; delete/agent/model use `Promise.allSettled` + `updateMany`-with-version-predicate, returning `affected[]` + `skipped[]` | Partial — bypasses spec's atomicity requirement | Friendlier UX (partial progress) but contradicts FR-015/025 |

**Best**: **AIB-821** — matches the auto-resolved CONSERVATIVE atomicity decision in the spec.

### Decision Point 2: Creator notifications (FR-029)
| Ticket | Approach |
|--------|----------|
| AIB-821 | Adds `Ticket.creatorId`, extends `Notification` (new `type`, `mergedIntoTicketId`, `ticketKeySnapshot`); inserts `Notification` rows inside the delete/merge transaction before `deleteMany` so `SetNull` retains key snapshot |
| AIB-820 | No schema change, no notifications emitted |

**Best**: **AIB-821** — only ticket that delivers FR-029.

### Decision Point 3: Conflict reporting contract
| Ticket | Response on stage drift / version mismatch |
|--------|---------------------------------------------|
| AIB-821 | `409 { code: 'BULK_CONFLICT_STAGE_DRIFT'\|'BULK_CONFLICT_VERSION', details.conflictingIds }` — entire batch rolled back |
| AIB-820 | `200 { affected, skipped: [{ ticketId, reason }] }` — silent partial application |

**Best**: **AIB-821** — explicit failure surface matches spec's "rejected with a message listing the conflicting tickets".

### Decision Point 4: UX surface
| Ticket | Approach |
|--------|----------|
| AIB-821 | Single inline `BulkActionBar` with `<Select>` dropdowns for agent/model, dedicated `BulkMergePreviewModal` + `BulkDeleteConfirmationModal` |
| AIB-820 | Separate dialogs (`BulkAgentDialog`, `BulkModelDialog`, `FusionDialog`) + toast summarizing `affected/skipped` |

**Best**: **AIB-820 (slight edge on polish)** — toast summaries and dedicated dialogs are nicer, but this is the only dimension where AIB-820 leads.

### Decision Point 5: Selection persistence after non-destructive action
| Ticket | Approach |
|--------|----------|
| AIB-821 | Keeps selection after agent/model (FR-004 met) |
| AIB-820 | Clears selection after every action |

**Best**: **AIB-821** — matches FR-004 (chain further actions on same batch).

## Ranking & Recommendation

### 1. **AIB-821** — Best implementation (88%)
**Why it wins**:
- True transactional atomicity across all four bulk ops (matches the spec's CONSERVATIVE auto-decision).
- Implements FR-029 creator notifications end-to-end (schema migration + tx-scoped insert).
- Explicit `BULK_CONFLICT_STAGE_DRIFT` / `BULK_CONFLICT_VERSION` contract that the client can act on.
- Preserves selection after non-destructive actions (FR-004).

### 2. **AIB-820** — (70%)
**Why it lost**:
- `Promise.allSettled` + `skipped[]` is best-effort, not atomic — violates FR-015/FR-025 and the auto-resolved atomicity decision.
- No creator notifications, no schema migration — FR-029 entirely unimplemented.
- Selection cleared after agent/model — fails FR-004 ("chain further actions").
- Slightly better dialog/toast UX is not enough to offset the spec gaps.
