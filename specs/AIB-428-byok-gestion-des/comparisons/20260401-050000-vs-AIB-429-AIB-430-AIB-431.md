## Implementation Choices Analysis

### [Spec] Server-side verification with distinct error codes (INVALID_KEY vs PROVIDER_UNREACHABLE)
| Ticket | Approach |
|--------|----------|
| AIB-428 | Full provider verification on save with distinct HTTP 422 codes (INVALID_KEY, PROVIDER_UNREACHABLE) |
| AIB-429 | Separate `/validate` endpoint, no verification on save |
| AIB-430 | Separate `/validate` endpoint, no inline save verification |
| AIB-431 | Server-side verification on save, returns readiness status with verification code |

**Best**: AIB-428 — Most complete error differentiation matching spec exactly.

### [Spec] Test existing credential against provider
| Ticket | Approach |
|--------|----------|
| AIB-428 | Dedicated `POST /credentials/[id]/test` endpoint updates readiness status |
| AIB-429 | Only validate with raw key (must re-enter) |
| AIB-430 | Only validate with raw key |
| AIB-431 | No dedicated test endpoint; readiness set on save only |

**Best**: AIB-428 — Only implementation with a proper "test existing" endpoint.

### Decision Point 1: Workflow credential guard strategy
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-428 | Guard in `dispatch-ai-board.ts` + workflow YAML fetch steps (2 workflows) | Yes | Pre-dispatch check, but only 2 workflows covered |
| AIB-429 | Modified `transition.ts` | Yes | Blocks at stage transition |
| AIB-430 | Shared bash script + 6 workflow YAML steps + `transition.ts` | Yes | Most comprehensive workflow coverage |
| AIB-431 | Guard in `jobs/route.ts` (job creation) + `transition.ts` + dedicated workflow endpoint | Yes | Blocks at API level before job creation, most robust |

**Best**: AIB-431 — Credential eligibility check at job creation API prevents invalid jobs from being created.

### Decision Point 2: API route structure
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-428 | `/api/credentials/*` + `/api/internal/credentials` | Partial | Simple but `/api/credentials` is generic naming |
| AIB-429 | `/api/credentials/*` + `/api/workflows/credentials` | Partial | Clear workflow separation |
| AIB-430 | `/api/user/ai-credentials/*` + `/api/projects/[id]/ai-credentials/owner` | Yes | RESTful, namespaced under user/project |
| AIB-431 | `/api/settings/ai-credentials/*` + `/api/internal/workflows/.../credential` | Yes | Settings-scoped, deeply nested workflow route |

**Best**: AIB-431 — Clean separation between user-facing settings routes and internal workflow routes.

### Decision Point 3: Component architecture
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-428 | 5 components (Form, List, Item, TestButton, DeleteDialog) | Yes | Good separation of concerns |
| AIB-429 | 2 components (Form, Card) | Partial | Simple but less modular |
| AIB-430 | 1 large component (253 lines) | No | Too large, violates component-driven principle |
| AIB-431 | 4 components (SettingsCard, List, SaveDialog, DeleteDialog) | Yes | Dialog-based UX, well-separated |

**Best**: AIB-428/431 — Both follow component-driven architecture properly.

### Decision Point 4: Type system and validation
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|

**Best**: AIB-431 — Fullest type coverage with dedicated validation schemas.
