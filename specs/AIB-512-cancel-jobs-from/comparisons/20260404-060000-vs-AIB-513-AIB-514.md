## Implementation Choices Analysis

### [Spec] Workflow 409 CANCELLED abort (CRITICAL)
| Ticket | Approach |
|--------|----------|
| AIB-512 | All 6 workflow YAMLs (speckit, quick-impl, verify, iterate, deploy-preview, rollback-reset) updated to check HTTP 409 on RUNNING callback and abort |
| AIB-513 | Only rollback-reset.yml and verify.yml updated; no 409 check in any workflow |
| AIB-514 | Only rollback-reset.yml and verify.yml updated; no 409 check in any workflow |

**Best**: AIB-512 — Without 409 abort, cancelled jobs continue running on GitHub Actions, defeating the purpose of cancel.

### [Spec] Race condition handling for already-terminal jobs
| Ticket | Approach |
|--------|----------|
| AIB-512 | Returns current status idempotently (200) with `alreadyTerminal: true` flag |
| AIB-513 | Returns 400 for non-cancellable states; idempotent only for CANCELLED |
| AIB-514 | Returns 400 for non-cancellable states |

**Best**: AIB-512 — Spec requires "no error shown to user" when job already completed; returning 400 triggers error toast.

### Decision Point 1: Cancel Workflow Module Architecture
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-512 | Dedicated `lib/workflows/cancel-workflow-run.ts` module, uses project's githubOwner/repo | Yes | Reusable, multi-repo compatible |
| AIB-513 | Dedicated `app/lib/workflows/cancel-workflow.ts` + `delete-branch.ts`, uses project data | Yes | Clean separation, test-mode aware |
| AIB-514 | Inlined Octokit in cancel route, uses env vars `GITHUB_OWNER`/`GITHUB_REPO` | No | Breaks multi-repo support |

**Best**: AIB-512/513 — AIB-514's use of env vars instead of project-specific owner/repo breaks multi-repository architecture.

### Decision Point 2: Rollback Transition Route Architecture
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-512 | `validateRollback()` + `rollbackTransaction()` helper functions; DRY | Yes | Minimal duplication |
| AIB-513 | Map-based validator lookup with dynamic response spread | Yes | Compact but harder to trace |
| AIB-514 | Separate if-blocks per rollback path (copy-paste pattern) | Yes | Readable but duplicated |

**Best**: AIB-512 — Best DRY balance with explicit helper functions.

### Decision Point 3: Rollback Confirmation UI
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-512 | Generic `RollbackConfirmationModal` component | Yes | Single modal, reusable |
| AIB-513 | `RollbackConfirmDialog` with typed `RollbackPath` enum + separate state variable | Yes | Type-safe but adds complexity with two rollback states |
| AIB-514 | Generic `RollbackConfirmationModal` using `ROLLBACK_MESSAGES` from validator | Yes | Clean data-driven approach |

**Best**: AIB-514 — Cleanest approach using shared `ROLLBACK_MESSAGES` constant and single state variable.

### Decision Point 4: Backup Tag Naming
| Ticket | Approach |
|--------|----------|
| AIB-512 | `backup/{ticketKey}/{stage}-{jobId}` with stage parameter passed to workflow |
| AIB-513 | `backup/{ticketKey}/rollback-{jobId}` (no stage distinction) |
| AIB-514 | `backup/{ticketKey}/reset-{jobId}` (no stage distinction) |

**Best**: AIB-512 — Stage-specific naming per spec (Decision 5), enables distinguishing build vs verify backups.

## Ranking & Recommendation

### 1. **AIB-512** - Best code (score: 86%)
**Why it wins**:
- Only implementation with complete workflow integration (all 6 YAMLs updated with 409 CANCELLED check)
- Idempotent cancel response for already-terminal jobs (spec-compliant)
- DRY rollback helpers, stage-specific backup tags
- Cancel from both board card AND ticket detail modal

### 2. **AIB-513** - (score: 79%)
**Why it lost**:
- Missing critical workflow YAML updates — cancel UI exists but workflows don't respect CANCELLED
- Best test coverage (7 files, 33%) but tests can't validate what doesn't exist
- Good code architecture with typed RollbackPath and separate modules

### 3. **AIB-514** - (score: 69%)
**Why it lost**:
- Same missing workflow YAML updates as AIB-513
- Uses env vars instead of project data for GitHub API (breaks multi-repo)
- Missing SPECIFY→INBOX branch deletion
- Fewest test files (3)
