## Implementation Choices Analysis

### [Spec] Workflow Availability Enforcement (FR-008/FR-009)
| Ticket | Approach |
|--------|----------|
| AIB-613 | Created standalone `lib/workflows.ts` with availability map, but not integrated into actual workflow dispatch |
| AIB-607 | `SETUP_INELIGIBLE_AGENTS` array in setup jobs route + workflow file updates for 3 supported workflows |
| AIB-612 | Explicit Gemini rejection blocks in ALL 5 unsupported workflow files (verify, assist, health-scan, onboard, retro-spec) |

**Best**: AIB-612 - Most thorough enforcement; prevents Gemini dispatch at both API and workflow levels.

### [Spec] Analytics Dynamic Agent Enumeration (FR-018/FR-019)
| Ticket | Approach |
|--------|----------|
| AIB-613 | Not implemented |
| AIB-607 | `Object.values(Agent)` iteration + `NamedAgent = Agent` type alias - fully dynamic |
| AIB-612 | Similar dynamic approach with `Object.values(Agent)` |

**Best**: AIB-607/AIB-612 tied - Both use dynamic Agent enum iteration, eliminating hardcoded agent arrays.

### Decision Point 1: Telemetry Collection Strategy
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-613 | Not implemented | N/A | No telemetry support |
| AIB-607 | Native OTLP env vars + server-side parsing of `gemini_cli.*` events | Yes | Lighter; depends on Gemini CLI OTLP support |
| AIB-612 | `--output-format stream-json` capture + `collect_gemini_telemetry()` jq parsing | Yes | More robust; doesn't require CLI OTLP support |

**Best**: AIB-607 - Cleaner architecture; leverages existing telemetry pipeline without adding a second collection path.

### Decision Point 2: Google API Key Verification Method
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-613 | API key via `x-goog-api-key` header; OAuth via userinfo endpoint | Partial | Different endpoints for different credential types |
| AIB-607 | API key as query param `?key=`; OAuth via Bearer on same models endpoint | Yes | Google's recommended approach; unified endpoint |
| AIB-612 | Same as AIB-607 (query param + unified endpoint) | Yes | Consistent with Google documentation |

**Best**: AIB-607 - Follows Google's official API key authentication pattern.

### Decision Point 3: Agent Icon SVG
| Ticket | Approach |
|--------|----------|
| AIB-613 | Generic layered geometric SVG (not Gemini brand) |
| AIB-607 | Official Gemini sparkle shape with blue-violet-pink gradient |
| AIB-612 | Same official Gemini sparkle shape with gradient |

**Best**: AIB-607/AIB-612 - Authentic Gemini brand icon.

### Decision Point 4: Schema Validation Approach
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-613 | Hardcoded string enums in Zod (`z.enum(['CLAUDE','CODEX','MISTRAL','GOOGLE'])`) | Partial | Must update every Zod schema when adding agents |
| AIB-607 | `z.nativeEnum(Agent)` from Prisma | Yes | Automatically supports new agents from schema |
| AIB-612 | Mix of `z.nativeEnum(Agent)` and hardcoded enums | Partial | Inconsistent approach across files |

**Best**: AIB-607 - Consistently uses `z.nativeEnum(Agent)`, eliminating future maintenance burden.

### Decision Point 5: Run-Agent Shell Script Design
| Ticket | Approach |
|--------|----------|
| AIB-613 | No changes to run-agent.sh |
| AIB-607 | `install_gemini` + `setup_gemini_telemetry` + `invoke_gemini` (minimal, piped stdin) |
| AIB-612 | `install_gemini` + `auth_gemini` + `invoke_gemini` + `collect_gemini_telemetry` (full lifecycle with error capture) |

**Best**: AIB-612 - Complete lifecycle management with proper auth setup and telemetry collection.
