## Implementation Choices Analysis

### [Spec] FR-005 — Source of per-turn context (no new runner instrumentation)
| Ticket | Approach |
|--------|----------|
| AIB-725 | Reads attended window from existing `claude_code.api_request` (input + cacheRead + cacheCreation) and Codex `*.token_usage` (`total_input`). Treats Gemini cumulative snapshots as peak-only. |
| AIB-734 | Listens for a `turn.completed` event with a `context_size` attribute that the agents do **not** currently emit. End result: no per-turn data is recorded for any real run. |
| AIB-735 | Same input + cacheRead + cacheCreation derivation as AIB-725, no Gemini handling. |
| AIB-736 | Counts only `input_tokens` for Claude — excludes cacheRead/cacheCreation so the "attended window" is undercounted. |

**Best**: AIB-725 — only implementation that derives the value from the attributes the existing telemetry stream actually carries.

### [Spec] FR-007 — Threshold semantics
| Ticket | Approach |
|--------|----------|
| AIB-725 | `getPeakContextThresholdState(peak, model)` divides by a model-specific window (Claude 200K, OpenAI 400K, Gemini 1M). 60% / 80% cutoffs. Neutral style below warning. |
| AIB-734 | Hard-coded 80K warning / 120K danger; same number for every model. Green "Healthy" badge below warning. |
| AIB-735 | Hard-coded 60K / 90K. Green "Healthy" label. |
| AIB-736 | Hard-coded 50K / 100K. Green "Healthy" pill. |

**Best**: AIB-725 — the only implementation whose colour matches "% of *the job's* model context window" as required by FR-007, and the only one that avoids the false-green reassurance the spec called out.

### [Spec] FR-011 — Analytics filters
| Ticket | Approach |
|--------|----------|
| AIB-725 | Per-chart selectors for command, workflowType, quality bucket — distribution updates client-side. |
| AIB-734 | Lifts the same three filters into the dashboard URL params and query payload. |
| AIB-735 | Distribution renders, but no command/workflow/quality filter exists. |
| AIB-736 | Distribution renders, no filters. |

**Best**: tie between AIB-725 and AIB-734.

### Decision Point — Schema field naming
| Ticket | Fields |
|--------|--------|
| AIB-725 | `peakContextTokens`, `avgContextTokens`, `turnCount` (matches existing `*Tokens` convention) |
| AIB-734 | `peakContextSize`, `averageContextSize`, `turnCount` |
| AIB-735 | `peakContextTokens`, `averageContextTokens`, `contextTurnCount` |
| AIB-736 | `peakContextTokens`, `avgContextTokens`, `turnCount` |

**Best**: AIB-725 / AIB-736 — align with `inputTokens`/`cacheReadTokens` style already on Job.

## Ranking & Recommendation

### 1. AIB-725 (source) — score 91%
**Why it wins**:
- Only ticket whose telemetry source matches what Claude/Codex actually emit.
- Only ticket whose threshold is a percentage of the *job's* model context window (FR-007).
- Avoids the false-green "Healthy" pill the spec explicitly warned against.
- Strongest test coverage (729 lines covering OTLP, thresholds, timeline, analytics).

### 2. AIB-735 — score 76%
**Why it lost**:
- Same correct telemetry derivation as AIB-725, but absolute thresholds (60K/90K) and missing analytics filters.

### 3. AIB-736 — score 72%
**Why it lost**:
- Counts only `input_tokens` (excludes cache_read/cache_creation), so the "attended window" peak is systematically too small.
- Absolute thresholds; no analytics filters.

### 4. AIB-734 — score 70%
**Why it lost**:
- Reads from a `turn.completed`/`context_size` attribute that agents do not emit — defeats FR-005 in practice (peak/avg/turn never populated).
- Absolute thresholds, despite adding the dashboard-level filters that AIB-735/AIB-736 lack.
