## Implementation Choices Analysis

### [Spec] Provider-type constraint (API_KEY only for OPENAI)
| Ticket | Approach |
|--------|----------|
| AIB-536 | Explicit `PROVIDER_ALLOWED_TYPES` constant validated at API route level before format/verify |
| AIB-537 | Relies on provider module to reject OAUTH_TOKEN (no explicit constraint at API boundary) |

**Best**: AIB-536 — Explicit constraint at API boundary follows defense-in-depth; clearer error message to callers.

### [Spec] Hardcoded CLAUDE commands use Anthropic credentials
| Ticket | Approach |
|--------|----------|
| AIB-536 | Updated `dispatch-ai-board.ts` and `dispatch-rollback-reset.ts` to pass correct provider |
| AIB-537 | No changes to dispatch files — hardcoded commands not updated |

**Best**: AIB-536 — FR-010 requires hardcoded CLAUDE commands always resolve Anthropic. AIB-537 leaves dispatch-ai-board.ts and dispatch-rollback-reset.ts untouched, risking incorrect credential resolution.

### [Spec] Health-scan credential resolution
| Ticket | Approach |
|--------|----------|
| AIB-536 | Updated `lib/health/scan-dispatch.ts` to use agent-based provider mapping |
| AIB-537 | No changes to health scan dispatch |

**Best**: AIB-536 — FR-013 explicitly requires health-scan dispatch to resolve credentials via agent/provider mapping.

### Decision Point 1: Provider Module Pattern
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-536 | `getProviderModule()` returns module object with typed interface | Yes (I. TypeScript-First) | Strong typing, extensible |
| AIB-537 | Wrapper functions `validateFormat(provider, ...)` that internally route | Yes (I. TypeScript-First) | Simpler API surface |

**Best**: AIB-536 — The module pattern with `Record<CredentialProvider, ProviderModule>` type provides compile-time guarantees that all providers implement the required interface. Both are valid; AIB-536 is slightly more maintainable for adding future providers.

### Decision Point 2: Environment Variable Mapping
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-536 | `getEnvVar(provider, type)` function with composite key `"PROVIDER:TYPE"` | Yes | Safe: throws on unmapped combos |
| AIB-537 | Nested `Record<Provider, Record<string, string>>` with `!` assertion | Yes | Simpler structure, but `!` assertion bypasses null safety |

**Best**: AIB-536 — The `getEnvVar()` function throws explicitly on unmapped combinations instead of silently producing `undefined`. More defensive.

### Decision Point 3: Test Coverage Strategy
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-536 | 3 integration + 1 component + 2 unit tests (470+ lines) | Yes (III. Test-Driven) | Comprehensive coverage across test pyramid |
| AIB-537 | 2 unit tests only (100 lines) | No (III violation) | Fast but no integration or component coverage |

**Best**: AIB-536 — Constitution §III mandates "No feature is complete without passing tests." Integration tests verify API routes, workflow credential resolution, and validation end-to-end. AIB-537 only tests pure functions.
