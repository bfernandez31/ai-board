## Implementation Choices Analysis

### [Spec] Independent storage for Claude vs. Codex per-stage config (FR-004) — the central architectural decision

| Ticket | Approach |
|--------|----------|
| AIB-830 | Adds 10 dedicated Codex columns: `codexSpecifyModel`, `codexPlanModel`, `codexImplementModel`, `codexQuickImplModel`, `codexVerifyModel` on both `Project` and `Ticket`, with a Prisma migration `20260530120000_aib_830_codex_per_stage_models`. Resolver scopes column reads to the active agent. Switching agents preserves both column sets. |
| AIB-831 | Reuses the existing `specifyModel`/`planModel`/… columns for both Claude and Codex. Validation switches to `anyModelIdSchema` (accepts either Claude or Codex IDs). When the owner selects Codex models and saves, the Claude selections are physically overwritten — they cannot coexist. |
| AIB-832 | Same shared-column approach as AIB-831. Adds a `getAgentModelMetadata()` registry in `lib/models/agent-models.ts` to factor Claude/Codex metadata behind one API, but the underlying storage is still a single column set. |

**Best**: **AIB-830** — directly satisfies FR-004, US2-AC3, US3-AC1, US3-AC2. AIB-831 and AIB-832 *cannot* satisfy these without a schema change.

### [Spec] Workflow dispatch routing of the resolved model

| Ticket | Approach |
|--------|----------|
| AIB-830 | Stage resolver returns a Codex model identifier when `effectiveAgent === CODEX`; dispatch path already established. |
| AIB-831 | No GitHub workflow YAML updates. The resolver picks a Codex model, but `speckit.yml`/`quick-impl.yml`/`verify.yml`/`inbox-analysis.yml` only forward `ANTHROPIC_MODEL`. The runner never receives `CODEX_MODEL`. |
| AIB-832 | Updates all 4 workflow YAMLs to route `inputs.model` to `ANTHROPIC_MODEL` when `agent==CLAUDE` and to `CODEX_MODEL` when `agent==CODEX`, with per-agent fallback defaults. Also adds `claude-opus-4-8` to the Claude whitelist. |

**Best**: **AIB-830** (resolver wired through existing path) and **AIB-832** (most explicit workflow wiring). AIB-831 leaves the dispatch chain broken.

### Decision Point: Resolver abstraction shape

| Ticket | Approach | Trade-offs |
|--------|----------|------------|
| AIB-830 | Inlines per-agent branch in `resolveStageModel`: separate `commandToStageModelKey` and `commandToCodexStageModelKey`, separate `codexSpecifyModel`-style fields in `TicketLikeForResolution`. Verbose but explicit. |
| AIB-831 | Single resolver path with an `AGENT_MODEL_CONFIG` partial-record (`{[CLAUDE]: {...}, [CODEX]: {...}}`) and a config lookup. Concise but pays the "any model in any column" architectural cost. |
| AIB-832 | Single resolver path delegating to `getAgentModelMetadata(agent)` registry. Cleanest abstraction of the three; reused in UI, validation, and dispatch. |

**Best**: **AIB-832** for abstraction quality — but the abstraction is built on a non-spec-compliant storage model. The pattern itself is worth porting onto AIB-830's schema.

### Decision Point: Codex model whitelist source

| Ticket | List | Match to spec FR-002 |
|--------|------|----------------------|
| AIB-830 | `gpt-5.5, gpt-5.4, gpt-5.4-mini, gpt-5.3-codex, gpt-5.2` | exact match |
| AIB-831 | `gpt-5-codex, gpt-5, gpt-5.4, gpt-5.5` | does not match |
| AIB-832 | `gpt-5.5, gpt-5.5-mini, gpt-5.5-codex, gpt-5.4, gpt-5.4-mini, gpt-5.4-codex` | does not match |

**Best**: **AIB-830** — the only ticket that adopted the curated list the spec explicitly auto-resolved with the PRAGMATIC policy.

## Ranking & Recommendation

### 1. **AIB-830** (source) — Best implementation (score: **86%**)

**Why it wins**:
- Only ticket that satisfies **FR-004** (independent storage) — the spec's central architectural requirement.
- Only ticket that satisfies **US3** in full (switch agent without losing config).
- Only ticket whose Codex model whitelist matches the spec-auto-resolved curated list (FR-002).
- Only ticket whose smart defaults match FR-009 exactly.
- Strongest test coverage (6 test files, including a dedicated integration test for the resolver and the smart-defaults endpoint).
- Adds a clean, reversible Prisma migration.

### 2. **AIB-832** (score: **66%**)

**Why it lost**:
- Reuses the existing Claude columns for Codex → cannot satisfy FR-004, US2-AC3, US3-AC1, US3-AC2 without a schema change.
- Codex model whitelist diverges from the spec (6 IDs with mini/codex variants vs. the spec's curated 5).
- Smart defaults pick `gpt-5.5-codex` for IMPLEMENT/QUICK-IMPL/VERIFY, not aligned with spec FR-009.

**What it does well** (worth borrowing):
- `lib/models/agent-models.ts` registry is the cleanest abstraction of the three — `getAgentModelMetadata(agent)` + `isConfigurableAgent` consolidate dispatch, UI, and validation behind one shape.
- Updates all 4 GitHub workflow YAMLs to route `inputs.model` to the correct runner env (`ANTHROPIC_MODEL` vs `CODEX_MODEL`) with explicit per-agent fallbacks.
- Bonus: adds `claude-opus-4-8` to the Claude whitelist.

### 3. **AIB-831** (score: **57%**)

**Why it lost**:
- Same FR-004 violation as AIB-832 (shared columns).
- **Missing the workflow-dispatch leg entirely** — no `.github/workflows/*.yml` changes. The resolver returns Codex model IDs that never reach the runner; effectively, US1-AC2 is broken end-to-end.
- Codex model whitelist diverges from the spec (4 IDs, none of `gpt-5.4-mini`, `gpt-5.3-codex`, or `gpt-5.2`).
- Smart defaults set `gpt-5.4` for QUICK-IMPL/VERIFY rather than the spec's `gpt-5.4-mini`.
- Weakest test coverage (2 test files).
