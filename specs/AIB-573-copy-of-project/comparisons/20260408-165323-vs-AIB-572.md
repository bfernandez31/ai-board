## Implementation Choices Analysis

### [Spec] Review artifacts in project settings (FR-023)

**Best**: AIB-573 — Fully implements FR-023; AIB-572 omits this requirement entirely.

### [Spec] Route imported projects to setup
| Ticket | Approach |
|--------|----------|
| AIB-573 | Centralized `resolveProjectSetupAccess()` utility reused across layout, settings, and board pages |
| AIB-572 | Direct Prisma query + redirect in setup page server component |

**Best**: AIB-573 — Access resolution is DRY and reusable across multiple entry points.

### Decision Point 1: Data Model Design
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-573 | `ProjectSetupJob` with 16 columns (dispatchKey, defaultBranch, commitSha, analysisSummary, artifactManifest, configPreview, errorCode) | Yes — V. Database Integrity | Rich metadata for debugging and audit; larger migration |
| AIB-572 | `SetupJob` with 11 columns (isPartial boolean, completedFiles text array) | Yes | Simpler, pragmatic; less operational data stored |

**Best**: AIB-573 — Richer model supports artifact manifest, analysis summary, config preview, and state transition validation (`assertAllowedTransition`). The stale job guard prevents race conditions. Aligns with Constitution V (database integrity).

### Decision Point 2: UI Component Architecture
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-573 | Single 300-line `setup-page-client.tsx` with inline sub-components | Partial — II. Component-Driven | Fewer files, but harder to test and maintain |
| AIB-572 | 5 decomposed components: AgentSelector, CredentialStatus, SetupProgress, SetupFileList, SetupWizard | Yes — II. Component-Driven | Better separation of concerns, individually testable |

**Best**: AIB-572 — Superior component decomposition follows Constitution II. Each component has a single responsibility and is independently testable.

### Decision Point 3: Agent Selection UI
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-573 | `<Select>` dropdown from shadcn/ui | Yes | Standard, compact |
| AIB-572 | `<RadioGroup>` with labels and agent icons | Yes | Better UX for 2 choices; all options visible |

**Best**: AIB-572 — RadioGroup is the correct UX pattern when there are only 2 options. Shows all choices at once.

### Decision Point 4: State Management Pattern
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-573 | Dual TanStack queries (state + status), `refetchInterval` based on status | Yes | Separates initial state load from polling |
| AIB-572 | Custom `useSetupJob` hook + wizard state machine (`WizardState` union type) | Yes | Explicit state transitions in UI, reusable hook |

**Best**: Tie — Both use TanStack Query correctly. AIB-573 separates state/status; AIB-572 encapsulates polling in a custom hook. Both valid approaches.

### Decision Point 5: Workflow Implementation
| Ticket | Approach | Constitution | Trade-offs |

### Decision Point 6: Service Layer Architecture
