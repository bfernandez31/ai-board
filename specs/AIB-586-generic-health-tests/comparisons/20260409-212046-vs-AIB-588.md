## Implementation Choices Analysis

### [Spec] FR-002: Framework-aware result parsing strategy
| Ticket | Approach |
|--------|----------|
| AIB-586 | 8 dedicated parsers in shell (vitest, jest, pytest, cargo-test, go-test, rspec, phpunit, playwright) with exit-code fallback |
| AIB-588 | Delegates to run-command.sh; uses exit code only (pass=1/fail=1) — no per-test result counts |

**Best**: AIB-586 — The spec requires "the appropriate result parsing strategy" per framework. AIB-586 implements all parsers including reporter flag injection. AIB-588 loses individual test counts entirely.

### [Spec] FR-005: Multi-framework parsing support
| Ticket | Approach |
|--------|----------|
| AIB-586 | parse_vitest_report(), parse_pytest_report(), parse_cargo_report(), parse_go_report(), parse_rspec_report(), parse_phpunit_report(), parse_playwright_report(), parse_exitcode_report() |
| AIB-588 | No framework-specific parsers; run_suite() returns "1 0 1" or "0 1 1" based on exit code |

**Best**: AIB-586 — This is a mandatory requirement ("MUST support result parsing for at least 5 frameworks"). AIB-586 fully implements it; AIB-588 does not.

### Decision Point 1: Script Architecture
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-586 | New plugin scripts (.claude-plugin/scripts/bash/) alongside existing | Neutral | Self-contained, no regression risk to existing scripts; more code |
| AIB-588 | Refactors existing scripts in-place (scripts/) | Better (DRY) | Less code, cleaner; but modifies working code |

**Best**: AIB-588 — Refactoring in-place is DRYer and avoids parallel codepaths. However, AIB-586's approach avoids regression risk.

### Decision Point 2: TypeScript Integration
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-586 | No TypeScript changes to lib/ | Violates I | Shell-only approach lacks type-safe config |
| AIB-588 | Adds Zod schemas (TestCapabilitiesSection), config-loader resolver, API route updates | Yes | Proper typed validation, cross-field integrity check |

**Best**: AIB-588 — Constitution Principle I requires TypeScript-First development. AIB-588 adds proper Zod schemas with cross-field validation (primaryCommandKey must reference existing command).

### Decision Point 3: Config Schema
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-586 | Adds `testing` section to config.yml (framework, e2e, e2e_framework) | Partial | Clean config structure but no runtime validation |
| AIB-588 | Adds `testCapabilities` section with Zod schema + superRefine cross-field check | Yes | Runtime-validated, type-safe, referential integrity |

**Best**: AIB-588 — Zod validation with referential integrity checks is significantly more robust.

### Decision Point 4: API/Platform Awareness
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-586 | No platform code changes (no lib/, no API route changes) | Missing | New capabilities invisible to platform |

**Best**: AIB-588 — API route and dispatch changes ensure the platform correctly handles TESTS scan SKIPPED status and passes target_repo_dir/ai_board_checkout_dir inputs.

## Ranking & Recommendation

### 1. **AIB-586** - Best code (score: 80%)
**Why it wins**:
- Fully implements FR-005 mandatory multi-framework parsing (8 parsers)
- Superior test coverage: 1581 lines across 7 dedicated test files including 710-line parser test suite
- Comprehensive spec fulfillment (100% of acceptance criteria met)
- Self-contained plugin approach eliminates regression risk

**Where it falls short**:
- No TypeScript lib/ changes (constitution principle I violation)
- No Zod config validation for new schema fields

- More total code (960 lines of new bash)

**Why it lost**:
- Missing FR-005: No per-framework test result parsing — run_suite() returns binary 1/0 pass/fail instead of actual test counts

- These are MUST requirements in the spec

**Where it excels**:
- Better TypeScript integration (Zod schemas, typed config)
- Better constitution compliance (88% vs 70%)
- Cleaner architecture with less code (474 vs 1218 added lines)
- Proper API/platform integration (scan-status route, dispatch inputs)
