# Implementation Plan: Admin Section with Claude Code Insights Report

**Branch**: `AIB-790-admin-section-with` | **Date**: 2026-05-11 | **Spec**: `specs/AIB-790-admin-section-with/spec.md`
**Input**: Feature specification from `specs/AIB-790-admin-section-with/spec.md`

## Summary

Add a new `/admin` area restricted to an env-var allowlist of admin emails, containing an Insights page that runs Claude Code's `/insights` analyzer over captured AI agent session artifacts. The page displays HTML reports in a sandboxed iframe, supports triggering new analysis runs, browsing past reports, and tracks run state persistently in the database. Reports are stored as Blob artifacts following the existing `@vercel/blob` pattern.

## Technical Context

**Language/Version**: TypeScript 5.9 (strict), Node.js 22.20.0
**Primary Dependencies**: Next.js 16 (App Router), React 18, Prisma 6.x, @vercel/blob, TanStack Query v5
**Storage**: PostgreSQL 14+ (InsightsRun model), Vercel Blob (HTML report artifacts)
**Testing**: Vitest (unit + integration), Playwright (E2E if browser-only behavior needed)
**Target Platform**: Vercel serverless (Next.js deployment)
**Project Type**: Web application (Next.js App Router)
**Performance Goals**: Page load < 3s (SC-001), 404 response < 1s (SC-002), trigger response < 2s (SC-003), report list load < 2s (SC-006)
**Constraints**: Report HTML rendered in sandboxed iframe (XSS prevention), admin allowlist via env var (< 20 users), no automated scheduling
**Scale/Scope**: < 100 reports total (manual-only triggers), < 20 admin users, cross-project analysis

## Implementation Phases

### Phase 1: Database + Admin Auth Foundation

**Goal**: InsightsRun model in database, admin access control working, env var configured.

1. Add `InsightsRunStatus` enum and `InsightsRun` model to `prisma/schema.prisma` (following HealthScan pattern)
2. Add `insightsRuns InsightsRun[]` relation to `User` model
3. Run `bunx prisma migrate dev` to generate migration
4. Create `lib/db/admin-auth.ts` with `verifyAdminAccess(request?)` function:
   - Call `requireAuth(request)` to get userId
   - Look up user email from DB
   - Parse `ADMIN_EMAILS` env var (comma-separated, trimmed, lowercased)
   - If empty/missing or email not in list → throw `"Not found"` (returns 404)
   - Return `{ userId, email }` for downstream use
5. Add `ADMIN_EMAILS` to `.env.example` with documentation
6. Write `tests/unit/lib/admin-auth.test.ts`:
   - Test: authorized email → returns user info
   - Test: unauthorized email → throws "Not found"
   - Test: empty env var → throws "Not found" (fail-closed)
   - Test: missing env var → throws "Not found" (fail-closed)
   - Test: case-insensitive matching
   - Test: whitespace trimming in env var parsing

### Phase 2: Blob Storage + Artifact Key Extensions

**Goal**: Blob client can upload and stream HTML reports.

1. Create `app/lib/insights/artifact-key.ts` with `buildInsightsReportKey(runId: number): string` → `insights-reports/<runId>.html`
2. Extend `app/lib/blob/client.ts`:
   - `uploadInsightsReport(key: string, html: Buffer): Promise<PutBlobResult>` — same pattern as `uploadJobLogArtifact` but `contentType: 'text/html; charset=utf-8'`
   - `streamInsightsReport(key: string): Promise<{ stream: ReadableStream<Uint8Array>; size: number } | null>` — same pattern as `streamJobLogArtifact`

### Phase 3: API Routes

**Goal**: Full CRUD lifecycle for insights runs, report streaming.

1. Create `app/api/admin/insights/runs/route.ts`:
   - **POST**: Trigger new run (follows health scan POST pattern from `app/api/projects/[projectId]/health/scans/route.ts:20-117`)
     - `verifyAdminAccess()` → check blob configured → check no active run → check new shipped tickets → create InsightsRun → start background analysis → return 201
   - **GET**: List runs with cursor pagination (follows health scan GET pattern from `app/api/projects/[projectId]/health/scans/route.ts:132-219`)
2. Create `app/api/admin/insights/runs/[runId]/route.ts`:
   - **GET**: Single run by ID
3. Create `app/api/admin/insights/runs/[runId]/status/route.ts`:
   - **PATCH**: Status update with transition validation (follows health scan PATCH pattern)
4. Create `app/api/admin/insights/runs/[runId]/report/route.ts`:
   - **GET**: Stream HTML from blob with `Content-Type: text/html`, `Cache-Control: private, max-age=3600`
5. Create `app/api/admin/insights/latest/route.ts`:
   - **GET**: Latest completed run + active run status (convenience for page load)
6. Write `tests/integration/admin/insights-runs.test.ts`:
   - Test POST trigger: creates run, returns 201
   - Test POST duplicate prevention: returns 409
   - Test POST no new tickets: returns 409 with last run date
   - Test GET list: pagination, filters
   - Test PATCH status transitions: valid and invalid
7. Write `tests/integration/admin/insights-access-control.test.ts`:
   - Test: admin user → 200/201 on all endpoints
   - Test: non-admin user → 404 on all endpoints
   - Test: unauthenticated → 404 on all endpoints

### Phase 4: Analysis Engine

**Goal**: Background process that collects sessions, downloads artifacts, runs /insights, uploads report.

1. Create `app/lib/insights/run-analysis.ts` with `executeInsightsAnalysis(runId: number)`:
   - Update run to RUNNING
   - Query shipped CLAUDE tickets with completed jobs that have `rawArtifactKey` (using `buildEffectiveAgentWhere('CLAUDE')` pattern from `lib/analytics/queries.ts:51-69`)
   - Download raw JSONL artifacts from blob to temp directory
   - Invoke Claude Code `/insights` CLI over the session files
   - Upload resulting HTML to blob via `uploadInsightsReport()`
   - Update run to COMPLETED with metadata (session count, ticket count, period, report key)
   - On any error: update run to FAILED with error message
   - Always cleanup temp directory (try/finally)
2. Integrate with POST trigger route: call `executeInsightsAnalysis(runId)` as non-blocking background work after creating the PENDING record

### Phase 5: Admin Pages + UI

**Goal**: Working admin layout with insights page, report viewer, trigger button.

1. Create `app/admin/layout.tsx` (server component):
   - Call `verifyAdminAccess()` → `notFound()` if throws
   - Render admin shell with sidebar and content area
   - Use aurora gradient styling for admin area header
2. Create `app/admin/page.tsx`:
   - `redirect('/admin/insights')` (only one admin page for now)
3. Create `components/admin/admin-sidebar.tsx` (client component):
   - Single nav item: "Insights" with icon (BarChart3 or similar from lucide-react)
   - Active state based on pathname (follows `components/navigation/icon-rail-sidebar.tsx` pattern)
4. Create `app/admin/insights/page.tsx` (server component):
   - Fetch latest completed run + active run status via server-side Prisma query
   - Pass initial data to client component
5. Create `components/admin/insights-dashboard.tsx` (client component):
   - TanStack Query polling for active run status (5s interval when a run is active, 30s otherwise)
   - "Run new analysis" button with loading/disabled states
   - Report list (newest first) with selectable entries
   - Empty state when no reports exist
   - Error display for failed runs with retry
   - Add `admin.insights` keys to `app/lib/query-keys.ts`
6. Create `components/admin/report-viewer.tsx` (client component):
   - Sandboxed iframe: `<iframe sandbox="" srcdoc={html} />`
   - No `allow-scripts`, no `allow-same-origin`
   - Auto-height adjustment via ResizeObserver or fixed height with scroll
   - Metadata header above iframe: generation date, period, session/ticket counts
7. Write `tests/unit/components/admin/insights-dashboard.test.tsx`:
   - Test: renders empty state when no reports
   - Test: renders latest report with metadata
   - Test: trigger button disabled during active run
   - Test: report list renders correctly

## Testing Strategy

Following constitution §III Test Selection Decision Tree:

| Test Type | Location | What it Covers |
|-----------|----------|---------------|
| Unit (Vitest) | `tests/unit/lib/admin-auth.test.ts` | Pure function: admin email allowlist parsing and matching |
| Unit (Vitest + RTL) | `tests/unit/components/admin/insights-dashboard.test.tsx` | Component rendering: empty state, report list, button states |
| Integration (Vitest) | `tests/integration/admin/insights-runs.test.ts` | API lifecycle: create run, list runs, status transitions, report streaming |
| Integration (Vitest) | `tests/integration/admin/insights-access-control.test.ts` | Access control: admin vs non-admin vs unauthenticated across all endpoints |

**No E2E tests**: The admin UI has no browser-only requirements (no OAuth, no drag-drop, no viewport-specific behavior). Integration tests adequately cover the API + access control surface. Component tests cover the UI rendering.

**Test patterns**: Integration tests follow the health scan test pattern (`tests/integration/health/trigger-scan.test.ts`). Component tests follow the analytics dashboard pattern (`tests/unit/components/analytics-dashboard.test.tsx`). Both use existing test helpers (`getTestContext()`, `renderWithProviders()`).
