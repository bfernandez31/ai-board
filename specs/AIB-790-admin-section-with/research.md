# Research: Admin Section with Claude Code Insights Report

**Branch**: `AIB-790-admin-section-with` | **Date**: 2026-05-11

## Technical Decisions

### 1. Admin Access Control Mechanism

- **Decision**: Environment variable allowlist (`ADMIN_EMAILS`) containing comma-separated user emails
- **Rationale**: Simplest secure mechanism. No DB migration for role system. Consistent with how `WORKFLOW_API_TOKEN` and `DEV_LOGIN_SECRET` are managed. The spec explicitly states "small number of users (under 20), changes infrequently."
- **Alternatives considered**:
  - Database-backed admin role: Over-engineered for < 20 users; adds migration, UI, and audit complexity for no practical benefit
  - User ID-based allowlist: Emails are more human-readable and debuggable; user IDs are opaque UUIDs

### 2. Admin Auth Helper Location

- **Decision**: New `lib/db/admin-auth.ts` with `verifyAdminAccess()` function
- **Rationale**: Follows the existing pattern in `lib/db/auth-helpers.ts` (verifyProjectAccess, verifyProjectOwnership). Returns 404 (not 403) per spec decision to not reveal admin area existence.
- **Alternatives considered**:
  - Middleware.ts: Project has no middleware; adding one for a single route group is inconsistent
  - Layout-only check: Doesn't protect API routes; auth must be enforced at both layout and API levels

### 3. InsightsRun State Machine

- **Decision**: New Prisma model `InsightsRun` with status enum `PENDING | RUNNING | COMPLETED | FAILED`
- **Rationale**: Mirrors HealthScan lifecycle pattern (same state machine, same API shape). Persistent state survives server restarts. Prevents double-trigger via DB constraint.
- **Alternatives considered**:
  - Reusing HealthScan model with new scanType: Violates single responsibility; HealthScan is project-scoped, InsightsRun is global/cross-project
  - In-memory state: Spec explicitly requires persistent tracking (FR-008)

### 4. Report Storage

- **Decision**: HTML reports stored in Vercel Blob (`reports/<runId>.html`) using existing `@vercel/blob` client pattern
- **Rationale**: Follows established artifact storage pattern from JobLog. Reports are potentially large HTML documents that shouldn't be in the database. The blob client (`app/lib/blob/client.ts`) is already battle-tested.
- **Alternatives considered**:
  - Database TEXT column: Would bloat backups and slow queries per spec auto-resolved decision
  - Filesystem: Not viable in serverless (Vercel) environment

### 5. Background Analysis Execution

- **Decision**: Server-side API route runs analysis synchronously within a long request (background via `waitUntil` or similar), NOT via GitHub Actions workflow
- **Rationale**: The analysis is a server-side operation that downloads blobs, runs Claude Code `/insights`, and uploads results. It doesn't need a repository checkout or workflow runner. The HealthScan workflow dispatch pattern is for operations that run inside the target repo — insights analysis operates purely on blob artifacts.
- **Alternatives considered**:
  - GitHub Actions workflow: Unnecessary infrastructure; analysis doesn't need repo access, just blob downloads + Claude Code CLI
  - Separate worker/cron: Out of scope per spec; manual trigger only

### 6. Report Rendering

- **Decision**: Sandboxed iframe (`sandbox` attribute with no permissions) for HTML report display
- **Rationale**: Spec auto-resolved decision (HIGH confidence). Report HTML is generated by an external tool — rendering inline creates XSS risk. Iframe with `sandbox` attribute and `srcdoc` prevents any script execution.
- **Alternatives considered**:
  - DOMPurify sanitization + inline: Can't guarantee completeness against evolving XSS vectors from arbitrary HTML
  - Pre-rendered React components: Would require re-implementing the `/insights` output format

## Patterns to Follow

### 1. Auth Error Pattern (from `lib/db/auth-helpers.ts:30-56`)

The app uses error-based auth: call `requireAuth()` which throws `"Unauthorized"`, then do a DB lookup that returns null if access denied:
```typescript
const userId = await requireAuth(request);
const resource = await prisma.model.findFirst({ where: { id, userId } });
if (!resource) throw new Error('Not found');
```
For admin routes, the pattern adapts: call `requireAuth()` to get userId, resolve email from DB, check against `ADMIN_EMAILS` env var. Throw `"Not found"` (not `"Forbidden"`) to return 404 per spec.

### 2. Background Job Lifecycle (from `app/api/projects/[projectId]/health/scans/route.ts:20-130`)

HealthScan POST follows: validate input → check for duplicate PENDING/RUNNING → find last COMPLETED for incremental base → create record with PENDING → dispatch background work → on dispatch failure, mark FAILED. InsightsRun will follow the same pattern but with inline async execution instead of workflow dispatch.

### 3. Blob Storage (from `app/lib/blob/client.ts:15-35`)

All blob operations use:
- `access: 'private'` — no world-readable URLs
- `addRandomSuffix: false` — deterministic keys
- `allowOverwrite: true` — retries overwrite
- Token from `requireToken()` helper
- 404 handling returns null (not throw)

For insights reports: key pattern `insights-reports/<runId>.html`, content type `text/html; charset=utf-8`, no gzip (HTML is typically small enough).

### 4. Effective Agent Filtering (from `lib/analytics/queries.ts:51-69`)

To filter for CLAUDE agent tickets, use the OR clause pattern:
```typescript
OR: [
  { agent: 'CLAUDE' },
  { agent: null, project: { is: { defaultAgent: 'CLAUDE' } } }
]
```
This handles tickets with explicit agent AND tickets inheriting from project default.

### 5. API Route Error Handling (from health scan routes)

Standard try/catch with error message matching:
```typescript
catch (error) {
  if (error instanceof Error) {
    if (error.message === 'Unauthorized') return 401;
    if (error.message === 'Not found') return 404;
  }
  console.error('[Context] Error:', error);
  return 500;
}
```
For admin routes: "Unauthorized" → redirect to signin; "Not found" → 404 (hides admin area).
