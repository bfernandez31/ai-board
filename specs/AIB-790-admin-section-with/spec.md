## User Scenarios & Testing

### User Story 1 - View Latest Insights Report (Priority: P1)

An authorized admin navigates to the Insights page and immediately sees the most recent analysis report rendered inline, along with metadata showing when the report was generated, the period it covers, and how many sessions and tickets were analyzed.

**Why this priority**: This is the core value of the feature — surfacing actionable insights from AI agent sessions. Without the ability to view reports, nothing else matters.

**Independent Test**: Can be fully tested by generating a report (or seeding one), navigating to /admin/insights, and verifying the report renders with correct metadata.

**Acceptance Scenarios**:

1. **Given** an authorized admin with at least one completed report, **When** they navigate to `/admin/insights`, **Then** they see the latest report rendered inline with a metadata header showing generation date, analyzed period, session count, and ticket count.
2. **Given** an authorized admin with no reports yet generated, **When** they navigate to `/admin/insights`, **Then** they see an empty state message indicating no reports have been generated, with the "Run new analysis" button prominently available.
3. **Given** a report covering sessions from multiple projects, **When** the admin views it, **Then** the metadata header explicitly states the analyzed scope (e.g., "Analyzed N Claude Code sessions across M tickets shipped between DATE and DATE").

---

### User Story 2 - Trigger New Analysis (Priority: P1)

An authorized admin clicks "Run new analysis" to generate a fresh insights report. The system checks whether there are new shipped tickets since the last run and either starts the analysis or explains why it cannot.

**Why this priority**: Equal priority with viewing — generating reports is the other essential capability. Without triggering, the page has nothing to display.

**Independent Test**: Can be tested by shipping at least one ticket with Claude agent sessions, clicking "Run new analysis", and verifying the job starts, shows a running state, and produces a new report on completion.

**Acceptance Scenarios**:

1. **Given** shipped tickets exist since the last report (or no report has ever been generated), **When** the admin clicks "Run new analysis", **Then** the system starts a background analysis job and the page shows a "Running..." indicator with the trigger button disabled.
2. **Given** no tickets have shipped since the last successful report, **When** the admin clicks "Run new analysis", **Then** the system displays a friendly message ("No new shipped tickets since last run on [DATE]") and does not start a job.
3. **Given** an analysis is already in progress, **When** the admin attempts to trigger another, **Then** the trigger button is disabled and the running state is visible, preventing double-trigger.
4. **Given** the analysis job completes successfully, **When** the admin is on the page, **Then** the new report appears as the latest, the running indicator disappears, and the report list updates.
5. **Given** the analysis job fails, **When** the admin is on the page, **Then** they see a clear error message indicating the failure and can retry.

---

### User Story 3 - Browse Past Reports (Priority: P2)

An authorized admin can see a chronological list of all past reports and select any one to view its full content and metadata.

**Why this priority**: Valuable for comparing trends over time, but secondary to viewing the latest report and being able to generate new ones.

**Independent Test**: Can be tested by generating multiple reports, navigating to the Insights page, and selecting different past reports from the list to verify each renders correctly.

**Acceptance Scenarios**:

1. **Given** multiple completed reports exist, **When** the admin views the Insights page, **Then** they see a chronological list (newest first) of past reports showing generation date and analyzed period.
2. **Given** the admin selects a past report from the list, **When** the selection is made, **Then** the selected report renders inline in place of the latest, with its corresponding metadata.
3. **Given** the admin is viewing a past report, **When** they select "Latest" or the most recent entry, **Then** the view returns to the latest report.

---

### User Story 4 - Admin Access Control (Priority: P1)

Only users on the configured admin allowlist can access the /admin area. Unauthorized users receive no indication that the area exists.

**Why this priority**: Security is non-negotiable — the admin area must be locked down before any content is served.

**Independent Test**: Can be tested by accessing /admin with an unauthorized user and verifying a 404 response, then accessing with an authorized user and verifying the admin layout loads.

**Acceptance Scenarios**:

1. **Given** an authenticated user who IS on the admin allowlist, **When** they navigate to `/admin` or `/admin/insights`, **Then** they see the admin layout with the Insights navigation entry.
2. **Given** an authenticated user who is NOT on the admin allowlist, **When** they navigate to `/admin` or `/admin/insights`, **Then** they receive a 404 response identical to a non-existent page.
3. **Given** an unauthenticated user, **When** they navigate to `/admin`, **Then** they are redirected to the sign-in page (standard auth flow) and after signing in, access is evaluated against the allowlist.

---

### Edge Cases

- What happens if the admin allowlist environment variable is empty or missing? The admin area is inaccessible to all users (fail-closed).
- What happens if a report generation job stalls indefinitely? A timeout mechanism marks the run as failed after a configurable period, allowing retrigger.
- What happens if the Blob storage token is not configured? The trigger is refused with a clear configuration error message; no partial work is done.
- What happens if a shipped ticket's Claude session artifact has been pruned (past retention window)? The analysis proceeds with available sessions only; the report metadata notes any gaps.
- What happens if a user is removed from the allowlist while viewing the admin page? Subsequent API calls return 404; the page becomes non-functional until they navigate away.
- What happens if the /insights analyzer produces no output or invalid HTML? The run is marked as failed with a descriptive error; no empty report is persisted.

## Requirements

### Functional Requirements

- **FR-001**: System MUST restrict the `/admin` area to users present on a configuration-driven allowlist, returning a 404 to all other users (authenticated or not).
- **FR-002**: System MUST provide an admin layout with a sidebar navigation containing one entry: "Insights".
- **FR-003**: System MUST display the most recent insights report rendered inline on the `/admin/insights` page, along with metadata (generation date, analyzed period, session count, ticket count).
- **FR-004**: System MUST display an empty state when no reports have been generated, guiding the admin to trigger the first analysis.
- **FR-005**: System MUST allow an admin to trigger a new analysis via a "Run new analysis" button.
- **FR-006**: System MUST perform a pre-flight check before launching analysis: verify that at least one ticket with a Claude agent session has shipped since the previous successful run. If none, refuse with a clear message including the date of the last run.
- **FR-007**: System MUST treat the first-ever analysis as covering all available Claude agent sessions across all shipped tickets.
- **FR-008**: System MUST track analysis run state persistently so that a running indicator survives page refreshes and server restarts.
- **FR-009**: System MUST prevent double-trigger: while an analysis is in progress, the trigger button is disabled and the running state is visible.
- **FR-010**: System MUST run the analysis as a background process that downloads raw Claude Code session artifacts, invokes the `/insights` analyzer, and persists the resulting HTML report with metadata.
- **FR-011**: System MUST filter analysis input to only include sessions from tickets where the agent is CLAUDE; sessions from other agents (Codex, Mistral, Gemini) are silently excluded.
- **FR-012**: System MUST persist completed reports as read-only artifacts with metadata including: generation timestamp, period start date, period end date, number of sessions analyzed, and number of tickets covered.
- **FR-013**: System MUST display a chronological list (newest first) of all past reports, each selectable to view inline.
- **FR-014**: System MUST handle analysis failures gracefully: display a clear error message to the admin and allow retry.
- **FR-015**: System MUST include the analyzed scope in the report metadata header (e.g., "Analyzed N Claude Code sessions across M tickets shipped between DATE and DATE").
- **FR-016**: System MUST fail closed when the admin allowlist configuration is empty or missing — no users gain admin access.

### Key Entities

- **InsightsRun**: Represents a single execution of the insights analysis. Tracks the trigger time, status (pending, running, completed, failed), completion time, the analyzed period (start/end dates), session count, ticket count, error information if failed, and a reference to the produced report artifact.
- **InsightsReport (artifact)**: The HTML output produced by the `/insights` analyzer, stored as a Blob artifact. Associated with an InsightsRun. Immutable once created.

### Internal Processes

- **Insights Analysis Run**: Triggered manually by an admin clicking "Run new analysis" on the Insights page.
  - **Input**: The time window to analyze (from last successful run's end date to now, or all-time for the first run). List of shipped tickets with agent=CLAUDE within that window. Raw Claude Code session artifact references for those tickets' jobs.
  - **Phases**:
    1. **Pre-flight validation** — Verify new shipped tickets exist since last successful run; refuse if none.
    2. **Session collection** — Identify all shipped CLAUDE tickets in the analysis window; resolve their jobs' raw session artifact references.
    3. **Artifact download** — Download raw Claude Code session JSONL artifacts from Blob storage to a temporary working area.
    4. **Insights analysis** — Invoke Claude Code's `/insights` analyzer over the collected session files to produce an HTML report.
    5. **Report persistence** — Upload the HTML report to Blob storage; update the InsightsRun record with completion status, metadata (session count, ticket count, period), and artifact reference.
    6. **Cleanup** — Remove temporary downloaded session files.
  - **Output**: A completed InsightsRun record with associated HTML report artifact in Blob storage. The Insights page reflects the new report as the latest.
  - **Error behavior**: If any phase fails, the run is marked as failed with a descriptive error message. Temporary files are cleaned up regardless of outcome. The admin can retry by triggering a new run. Partial results are not persisted — a run either produces a complete report or is marked failed.

## Success Criteria

### Measurable Outcomes

- **SC-001**: Authorized admins can access the Insights page and view the latest report within 3 seconds of navigation.
- **SC-002**: Unauthorized users receive a 404 response within 1 second, with no information leakage about the admin area.
- **SC-003**: The "Run new analysis" trigger correctly identifies whether new shipped tickets exist and responds (start or refuse) within 2 seconds.
- **SC-004**: 100% of completed analysis runs produce a viewable HTML report with accurate metadata matching the actual sessions analyzed.
- **SC-005**: The system prevents 100% of double-trigger attempts — no two analysis runs execute concurrently.
- **SC-006**: Past reports are browsable and individually viewable, with the list loading within 2 seconds regardless of report count (up to 100 reports).
- **SC-007**: The report content is the genuine output of Claude Code's `/insights` analyzer, containing narratives, friction categories, suggested CLAUDE.md additions, and other standard sections — not a re-implementation or summary.
- **SC-008**: Only Claude agent sessions appear in the analysis input; sessions from other agents are excluded with 100% accuracy.

## Assumptions

- The raw Claude Code session JSONL artifacts (from the "Capture native Claude Code session JSONL" feature) are available in Blob storage before this feature is used.
- Claude Code's `/insights` command accepts a directory of session JSONL files and produces a self-contained HTML report.
- The admin allowlist will contain a small number of users (under 20) and changes infrequently.
- The Blob storage token (`BLOB_READ_WRITE_TOKEN`) is provisioned in all environments where this feature runs.
- Shipped tickets are identified by `stage = SHIP` in the ticket model.
- Report generation time depends on the number of sessions but is expected to complete within minutes, not hours.

## Dependencies

- **AIB-789 (or equivalent)**: "Capture native Claude Code session JSONL alongside normalized logs" must be merged. Without raw native session artifacts in Blob storage, the `/insights` analyzer has no input data.
- **Blob storage infrastructure**: `BLOB_READ_WRITE_TOKEN` must be configured.
- **Claude Code CLI**: Must be available in the execution environment where the analysis background job runs, with the `/insights` command accessible.

## Out of Scope

- No other admin pages (no global stats, no evals, no user management UI).
- No database-backed admin role system — configuration-driven allowlist only.
- No automated scheduling (no cron, no nightly runs).
- No multi-agent analysis (Codex, Mistral, Gemini sessions excluded).
- No filters, search, or custom date range selection on the report list.
- No editing or annotating reports.
- No notifications or emails when a run completes.
