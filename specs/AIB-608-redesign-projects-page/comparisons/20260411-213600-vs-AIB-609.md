## Implementation Choices Analysis

### [Spec] Plan-aware visual styling
| Ticket | Approach |
|--------|----------|
| AIB-608 | `getBannerStyles()` helper returning Tailwind gradient classes via `cn()`, uses shadcn `Badge` for plan label |
| AIB-609 | `planConfig` record with aurora CSS utility classes in `globals.css`, custom `<span>` for plan label |

**Best**: AIB-608 - Uses shadcn `Badge` component as required by constitution II ("Use shadcn/ui components exclusively for UI primitives"). AIB-609's custom span violates this principle.

### [Spec] Loading skeleton
| Ticket | Approach |
|--------|----------|
| AIB-608 | `UsageBannerSkeleton` with `min-h-24` matching final height, uses shadcn `Skeleton` |
| AIB-609 | `PlanBannerSkeleton` using shadcn `Skeleton` with fixed `h-14` |

**Best**: AIB-608 - `min-h-24` provides more flexible layout stability than fixed `h-14`.

### Decision Point 1: File strategy (modify vs create)
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-608 | Modifies `usage-banner.tsx` in-place | Yes | No dead code, clean history |
| AIB-609 | Creates new `plan-banner-card.tsx`, leaves `usage-banner.tsx` as dead code | No | Dead code remains, file bloat |

**Best**: AIB-608 - CLAUDE.md states "prefer editing an existing file to creating a new one." AIB-609 leaves `usage-banner.tsx` unused but not deleted.

### Decision Point 2: Type imports
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-608 | Imports `UsageData` from hook (`@/hooks/use-usage`) | Yes | Proper layer separation |
| AIB-609 | Imports `SubscriptionPlan` from `@prisma/client` | Concern | Couples UI to ORM layer |

**Best**: AIB-608 - Using hook-exported types maintains proper layer boundaries. Importing Prisma types directly into UI components creates unnecessary coupling.

### Decision Point 3: Test patterns
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-608 | Factory pattern (`createUsageData()`) + `renderBanner()` helper, 5 tests | Yes | DRY, maintainable |
| AIB-609 | Inline mock data per test, 7 tests | Yes | More verbose, but explicit |

**Best**: AIB-608 - Factory pattern is more maintainable; when `UsageData` shape changes, only one place to update.
