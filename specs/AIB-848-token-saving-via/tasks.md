## Dependencies & Execution Order

### Phase Dependencies

- **Setup (Phase 1)**: No dependencies; can start immediately.
- **Foundational (Phase 2)**: Depends on Setup; blocks all user stories because Prisma fields, shared validation, and resolver helpers are required everywhere.
- **User Story 1 (Phase 3)**: Depends on Foundational; delivers the MVP project default, workflow activation, and job reporting.
- **User Story 2 (Phase 4)**: Depends on Foundational; can proceed in parallel with parts of US1, but final transition assertions need the US1 job-capture path.
- **User Story 3 (Phase 5)**: Depends on US2 API/derived-state fields; consolidates the user-facing edit surface.
- **User Story 4 (Phase 6)**: Depends on US1 job fields and US2 ticket override fields; preserves and displays comparison telemetry.
- **Polish (Phase 7)**: Depends on all desired user stories being complete.

### User Story Dependencies

- **US1 (P1)**: Required for MVP. No dependency on other stories after Foundational.
- **US2 (P1)**: Backend/API work can start after Foundational; full validation of future-run capture uses US1 transition persistence.
- **US3 (P2)**: Requires US2 ticket response fields and save behavior.
- **US4 (P3)**: Requires US1 job telemetry fields and US2 ticket override persistence.

### Dependency Graph

```text
Setup
  -> Foundational
    -> US1 Enable token saving for Claude runs
    -> US2 Override token saving per ticket
      -> US3 Unified Run settings dialog
    -> US4 Compare real savings with cloned tickets

Recommended sequential completion: US1 -> US2 -> US3 -> US4
MVP scope: US1 only, after Setup and Foundational
```

### Within Each User Story

- Tests must be written first and fail before implementation.
- Schema and resolver changes precede route and workflow implementation.
- API and persistence changes precede UI wiring.
- Core implementation precedes integration, type-check, and lint.
