## Implementation Choices Analysis

### [Spec] Pairing trigger architecture
| Ticket | Approach |
|--------|----------|
| AIB-773 | SHIP transition fires-and-forgets `pairAnalysisWithOutcome`; persists pending row when outcome missing; `nightly-pairing-sweep.yml` cron sweeps pending and catch-up windows. |
| AIB-744 | Pairing only invoked **after** `captureOutcomeOnShip` resolves; no pending row needed; no retry sweep. |

**Best**: AIB-744 — eliminates a race-condition class entirely; AIB-773 needs additional infrastructure (cron + maintenance endpoint + pending state) to compensate.

### [Spec] Cost prediction modeling
| Ticket | Approach |
|--------|----------|
| AIB-773 | Single envelope `[baselineLowerUsd, marginalFrictionUpperUsd]`. |
| AIB-744 | Decomposed (baseline lower/upper + marginal lower/upper + summed lower/upper) — matches user-facing "expected cost" line; preserves drill-down without re-derivation. |

**Best**: AIB-744 — richer audit data without remigration cost.

### [Spec] Recommendation scoring axes
| Ticket | Approach |
|--------|----------|
| AIB-773 | Single `frictionMatch` + auxiliary `frictionEmerged`. |
| AIB-744 | Two axes: `recommendationMatched` (followed?) AND `recommendationFrictionAligned` (right in hindsight?), persisted independently. |

**Best**: AIB-744 — directly addresses spec's "compared against the workflow type that was actually used and against whether friction emerged regardless".

### Decision Point: Module structure
| Ticket | Approach |
|--------|----------|
| AIB-773 | `lib/drift/{pair, persist, compute-deltas, queries, sweep, types}.ts` — flat. |
| AIB-744 | `lib/calibration/{pair, derive, persist, serialize, queries, types}.ts` — adds explicit derive/serialize separation. |

**Best**: AIB-744 — cleaner separation of pure derivation from persistence and DTO shaping.

### Decision Point: Persistence validation
| Ticket | Approach |
|--------|----------|
| AIB-773 | Direct Prisma write, no schema-side validation. |
| AIB-744 | Zod `superRefine` validates invariants (binarisation rule, range bounds, partial-reason enum) before write. |

**Best**: AIB-744 — Constitution principle IV (Security-First) calls for input validation; this is internal but still safer.

### Decision Point: Pagination
| Ticket | Approach |
|--------|----------|
| AIB-773 | Cursor pagination (base64 `{shippedAt, id}`), pageSize 1–50. |
| AIB-744 | Fixed `take: 30`, no pagination. |

**Best**: AIB-773 — fulfills FR-012 ("when more exist they MUST also be available, with pagination if needed").

## Ranking & Recommendation

### 1. **AIB-744** — Best code (score: 89%)
**Why it wins**:
- **Test depth**: 14 tests covering the spec's edge cases verbatim (cold-start, multi-analysis, partial outcome, immutability, no-success, dashboard window).
- **Cleaner architecture**: derive/serialize/persist/queries split; Zod superRefine guards persistence invariants.
- **Sharper modeling**: dual recommendation axes, decomposed cost components, explicit verdict enum that supports `n_a` distinctly from miss.
- **Race-free trigger**: pairing runs after outcome capture completes, removing a whole class of bugs (and the cron + pending-row machinery they require).

### 2. **AIB-773** (source) — score: 81%
**Why it lost**:
- **Test coverage**: 6 tests vs 14 — many spec edge cases (cold-start exclusion, multi-analysis selection, partial outcomes, no-success exclusion) are not directly asserted.
- **Persistence invariants** not validated; relies on caller correctness.
- **Cost/recommendation modeling** is single-envelope and single-axis; loses audit fidelity.

**Where AIB-773 is genuinely stronger**:
- Cost/quality panels expose the under/over split explicitly (FR-009/FR-010 letter-of-the-spec).
- Cursor pagination on the dashboard endpoint (FR-012 letter-of-the-spec).
- Explicit 24h retry sweep + cron, even though architecturally it should be unnecessary.
