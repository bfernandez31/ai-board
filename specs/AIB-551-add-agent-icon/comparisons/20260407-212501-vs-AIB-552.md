## Implementation Choices Analysis

**Best**: AIB-552 — Handles agent identifiers like "claude-opus" or "codex-mini-latest" that don't match enum values exactly, making it more robust against real-world data.

### Decision Point 1: Component Architecture
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-551 | Two separate exports: `WorkflowTypeBadge`, `AgentTooltipIcon` | Partial — two imports per consumer | Simpler individual components |
| AIB-552 | Single `ComparisonCardMetadata` composite with internal `WorkflowTypeBadge` | Yes — single composable import | Better encapsulation, single integration point |

**Best**: AIB-552 — Reduces import surface and co-locates related logic. Follows constitution §II (Component-Driven Architecture).

### Decision Point 2: TypeScript Discipline
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-551 | No explicit interfaces for existing types, no return type annotations | Warning — implicit types | Faster to write |
| AIB-552 | Extracted `EnrichmentValue`, `GradientTheme`, `StatPillTheme` interfaces, explicit `: JSX.Element` returns | Yes — explicit types | More verbose but catches refactor errors |

**Best**: AIB-552 — Constitution §I (TypeScript-First) requires explicit type annotations. AIB-552 adds named interfaces where AIB-551 relies on anonymous inline types.

### Decision Point 3: Agent Data Handling
| Ticket | Approach | Constitution | Trade-offs |

**Best**: AIB-552 — Real comparison data stores model identifiers (e.g., "claude-opus-4-6"), not enum values. AIB-552 handles this correctly.
