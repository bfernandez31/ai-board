## Implementation Choices Analysis

### [Spec] FR-004 — RTK install & activation
| Ticket | Approach |
|--------|----------|
| AIB-851 | `npm install -g @anthropic-ai/rtk` + `export CLAUDE_CODE_PRETOOLS_HOOK="rtk compress"` — package name does not match the real RTK (Rust tool at `rtk-ai/rtk`) and the env-var hook is not a documented Claude Code mechanism. Likely never activates → always falls back. |
| AIB-848 | Official `install.sh` with cargo fallback, then `rtk init -g --auto-patch` **and verifies** the hook registered via `rtk init --show`. Robust, unpinned. |
| AIB-849 | Pinned `RTK_VERSION=0.5.0` via versioned `install.sh`, then `rtk init --global` + `rtk --version` check. Security-first (no `latest`). |

**Best**: AIB-849 — functional + supply-chain-safe. AIB-848 close (verifies hook, but unpinned). AIB-851 activation path is questionable.

### [Spec] FR-014 — Iterate-stage coverage
| Ticket | Approach |
|--------|----------|
| AIB-851 | Wires `token_saving` into iterate.yml. |
| AIB-848 | iterate.yml NOT modified — token saving silently absent on iterate runs. |
| AIB-849 | Wires `tokenSaving` into iterate.yml. |

**Best**: AIB-851/AIB-849 — spec explicitly scopes token saving to iterate.

### [Spec] FR-007 — Job status modeling
| Ticket | Approach |
|--------|----------|
| AIB-851 | `tokenSavingStatus String?` — free string, lowercase values. Weak typing. |
| AIB-848 | `TokenSavingRunStatus` enum (5 states) + `tokenSavingFallbackReason` text. Most diagnosable. |
| AIB-849 | `TokenSavingOutcome` enum (3 states). Clean. |

**Best**: AIB-848 — actionable fallback reason matches spec intent.

### Decision Point: Status-route integration (DRY)
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-851 | Inline checks duplicated in both PATCH paths, untyped | Warning (I) | Least DRY |
| AIB-848 | Dedicated `buildTokenSavingPatch` helper, reused both paths | Yes | DRY, enum-typed |
| AIB-849 | Folded into existing `buildVersionPatch` first-write-wins helper | Yes | Most DRY, mirrors AIB-779 pattern |

**Best**: AIB-849 — extends the existing pattern with least new surface.

### Decision Point: Override data model
| Ticket | Approach |
|--------|----------|
| AIB-851 | `tokenSaving Boolean?` (null/true/false) — mirrors agent/policy nullable pattern |
| AIB-848 | `TokenSavingOverride` enum (FORCE_ON/FORCE_OFF) + dedicated resolution module |
| AIB-849 | `tokenSaving Boolean?` + dedicated REST endpoint w/ optimistic-concurrency `version` + discriminated-union result |

**Best**: Tie 848/849 — both explicit and type-safe; 851 acceptable but pairs it with an untyped job status.

## Ranking & Recommendation

### 1. **AIB-849** — Best code (score: 92%)
**Why it wins**:
- Full spec coverage (only ticket with FR-004 + FR-012 + FR-014 all met).

**Why it lost**:
- Core FR-004 activation is questionable: `@anthropic-ai/rtk` npm package does not match the real RTK tool, and `CLAUDE_CODE_PRETOOLS_HOOK` is not a documented hook mechanism — RTK likely never activates.
- Untyped `string` job status (constitution I warning).
- Lowest test coverage (22%) and least-DRY status-route logic.
