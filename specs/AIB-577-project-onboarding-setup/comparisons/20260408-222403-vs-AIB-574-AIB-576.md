## Implementation Choices Analysis

### [Spec] FR-001: Redirect imported projects without config to setup
| Ticket | Approach |
|--------|----------|
| AIB-577 | Adds redirect check in board/page.tsx: `if (project && !project.configSyncedAt)` |
| AIB-574 | No change to board/page.tsx; setup page exists but board doesn't redirect |
| AIB-576 | Adds `isSetupRequired()` check in board/page.tsx + new entry page.tsx + project-card routing |

**Best**: AIB-576 - Most comprehensive routing with entry page, board redirect, and project card integration.

### [Spec] FR-003/004: Credential verification before dispatch
| Ticket | Approach |
|--------|----------|
| AIB-577 | Dedicated `/setup/credential-check` endpoint with Zod validation, server-side per-project check |
| AIB-574 | Client-side check via global `/api/credentials` endpoint, filters on client |
| AIB-576 | Server-side `getOwnerCredentialReadiness()` with structured readiness enum (MISSING/PENDING_VERIFICATION/READY/ACTION_REQUIRED) |

**Best**: AIB-576 - Most thorough with typed readiness states; AIB-574 has security concern with client-side check.

### [Spec] FR-013: Owner-only access
| Ticket | Approach |
|--------|----------|
| AIB-577 | Server component checks `project.userId !== userId`, renders "Access Denied" for non-owners |
| AIB-574 | Passes `isOwner` prop to client, allows members to view page, blocks dispatch only |
| AIB-576 | Server-side `viewerCanManage` flag, read-only Alert for non-owners, clear distinction |

**Best**: AIB-577/576 tie - Both properly restrict access.

### Decision Point 1: API Architecture
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-577 | `/setup/jobs` (POST/GET) + `/setup/jobs/[jobId]/status` (PATCH) + `/setup/credential-check` | Yes | Clean REST, 3 dedicated endpoints |
| AIB-574 | `/setup` (POST/GET) + `/setup/status` (PATCH) | Yes | Simpler, combined endpoints |
| AIB-576 | `/setup` (GET) + `/setup/attempts` (POST) + `/setup/attempts/[attemptId]/status` (PATCH) | Yes | Most RESTful, proper resource naming |

**Best**: AIB-576 - RESTful "attempts" naming supports retry history naturally.

### Decision Point 2: Service Layer Architecture
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-577 | Logic inline in route handlers | Partial | Simple but less testable |
| AIB-574 | Logic inline in route handlers, reuses `canTransition`/`isTerminalStatus` from job-state-machine | Partial | Reuses existing utilities |
| AIB-576 | Dedicated `lib/project-setup/` module (service.ts, state.ts, types.ts, workflow-dispatch.ts) | Yes | Highly organized, testable, follows constitution II |

**Best**: AIB-576 - Proper separation of concerns per constitution II (feature-based structure).

### Decision Point 3: Database Model
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|

**Best**: AIB-576 - Unique `(projectId, attemptNumber)` constraint and structured failure fields.

### Decision Point 4: Workflow Dispatch Security

## Ranking & Recommendation

### 1. **AIB-576** - Best code (score: 95%)
**Why it wins**:
- Comprehensive `lib/project-setup/` service layer with proper separation (types, state, service, dispatch)
- Richest database model with `attemptNumber` unique constraint and structured failure tracking
- Deepest test coverage (9 test files, extends 6 existing test suites)
- Proper codebase integration (project card routing, import flow, config-sync enhancement)
- Discriminated union state types for exhaustive checking
- Secure workflow dispatch using secrets

### 2. **AIB-577** (source) - Strong implementation (score: 90%)
**Why it's second**:
- 100% spec fulfillment with clean, focused implementation
- Proper credential check endpoint and secure workflow dispatch
- Good test coverage (3 files) but less comprehensive than AIB-576
- Inline route logic instead of service layer (simpler but less organized)

### 3. **AIB-574** - Weakest (score: 77%)
**Why it lost**:
- **Security vulnerability**: exposes workflow API token as dispatch input
- Missing board-to-setup redirect (FR-001 not met)
- Client-side credential checking (less secure than server-side)
- No startedAt tracking on RUNNING transition
- Less robust state management
