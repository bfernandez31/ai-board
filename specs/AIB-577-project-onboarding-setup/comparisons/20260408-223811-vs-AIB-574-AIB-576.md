## Implementation Choices Analysis

### [Spec] Completion triggers config sync + board redirect
| Ticket | Approach |
|--------|----------|
| AIB-577 | Non-blocking `.catch()` on config sync; polls until `configSyncedAt` is set at 2s intervals; client-side redirect |
| AIB-574 | Synchronous `await syncProjectConfig()` in callback handler (blocks response); polls at 2s; `CONFIGURED` state triggers redirect |
| AIB-576 | Non-blocking config sync; polls at **15s intervals** (too slow for SC-005's 2s requirement); server-side redirect via page component |

**Best**: AIB-577 - Non-blocking sync + fast polling. AIB-576's 15s interval violates the spec's 2-second responsiveness criterion.

### [Spec] Prevent duplicate dispatch (race condition safety)
| Ticket | Approach |
|--------|----------|
| AIB-577 | Wraps active-job check + job creation in `prisma.$transaction()` — atomic, no race window |
| AIB-574 | Sequential check-then-create without transaction — concurrent requests can bypass the guard |
| AIB-576 | Service layer handles check logic (likely non-atomic but encapsulated) |

**Best**: AIB-577 - Transaction eliminates the race condition per Constitution V (Database Integrity: "Use Prisma transactions for operations affecting multiple tables").

### Decision Point 1: Workflow Secret Management
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-577 | Uses `${{ secrets.WORKFLOW_API_TOKEN }}` in workflow YAML | Yes (IV) | Token never visible in workflow inputs |
| AIB-574 | Passes `workflowToken` as workflow dispatch input | **No** (IV violation) | Token appears in GH Actions inputs UI |
| AIB-576 | Uses `${{ secrets.WORKFLOW_API_TOKEN }}` in workflow YAML | Yes (IV) | Token never visible in workflow inputs |

**Best**: AIB-577/AIB-576 - AIB-574 exposes the workflow API token as a plain-text workflow input, violating Constitution IV ("Never expose sensitive data").

### Decision Point 2: API Route Structure
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-577 | 3 dedicated routes: `/setup/credential-check`, `/setup/jobs`, `/setup/jobs/[jobId]/status` | Yes (II) | Clear separation of concerns, each route has single responsibility |
| AIB-574 | 2 routes: `/setup` (GET state + POST dispatch), `/setup/status` (PATCH callback) | Yes (II) | Pragmatic, fewer files; GET/POST combined in one route |
| AIB-576 | 3 routes: `/setup`, `/setup/attempts`, `/setup/attempts/[attemptId]/status` | Yes (II) | Clean REST semantics with "attempts" resource |

**Best**: AIB-577 - Dedicated credential-check endpoint follows single responsibility. AIB-576 is also clean but adds unnecessary complexity.

### Decision Point 3: State Management Pattern
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-577 | `useSetupJobPolling` custom hook with TanStack Query, job status derived client-side | Yes | Simple, raw job data polling with smart refetchInterval |
| AIB-574 | `useSetupPolling` with server-derived `SetupState` enum, TanStack Query | Yes | Server owns state derivation, cleaner client logic |
| AIB-576 | TanStack Query in `ProjectSetupPage`, `queryClient.setQueryData` for optimistic updates | Yes | Optimistic update on dispatch, but 15s polling |

**Best**: AIB-574 - Server-derived state enum reduces client-side logic duplication, though AIB-577's approach is simpler.

### Decision Point 4: Code Organization
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-577 | Feature folder `components/setup/`, dedicated `lib/workflows/dispatch-onboard.ts` | Yes (II) | Clean, minimal file footprint |
| AIB-574 | Feature folder `components/setup/`, dispatch inline in API route | Yes (II) | Less abstraction, simpler but dispatch logic mixed with handler |
| AIB-576 | `lib/project-setup/{service,state,types,workflow-dispatch}.ts` + 3 components | Yes (II) | Most modular but over-engineered for scope |

**Best**: AIB-577 - Right level of abstraction. AIB-576 over-engineers with 4 lib files for a focused feature.

## Ranking & Recommendation

### 1. **AIB-577** - Best code (score: 91%)
**Why it wins**:
- Atomic transaction for race-condition-free job creation (Constitution V)
- Secure secret management via GitHub Secrets, not workflow inputs (Constitution IV)
- Non-blocking config sync avoids blocking the callback response
- Clean, right-sized architecture — not over-engineered
- Fast 2s polling meets SC-005 responsiveness

### 2. **AIB-576** - (score: 85%)
**Why it lost**:
- Over-engineered: 24 source files, 4 dedicated lib modules for a single feature
- 15s polling is too slow for the spec's 2-second responsiveness target
- Modifies unrelated files (.prettierignore)
- Wider blast radius: touches import route, project card, and existing project API

### 3. **AIB-574** - (score: 82%)
**Why it lost**:
- Security violation: exposes WORKFLOW_API_TOKEN as workflow dispatch input
- No transaction on check-then-create — race condition vulnerability
- Synchronous config sync blocks callback response
- Best test coverage (4 files including hook unit test) is a strength but doesn't outweigh security/integrity issues
