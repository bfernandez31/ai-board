## Implementation Choices Analysis

### [Spec] Post-dismissal access to Generate Specs (US2.2)
| Ticket | Approach |
|--------|----------|
| AIB-585 | Board menu integration — "Generate Specs" option accessible after banner dismissal |
| AIB-587 | Setup page only — no board-level re-entry point after dismissal |

**Best**: AIB-585 — Users stay on the board; setup page is for first-time init only.

### [Spec] Setup page redirect on configSyncedAt (US3.1-3)
| Ticket | Approach |
|--------|----------|
| AIB-585 | No setup page changes — does not address redirect bug |
| AIB-587 | Full Step 2 integration with auto-redirect, step indicators, skip button |

**Best**: AIB-587 — Fully implements the setup page redirect requirement.

### Decision Point 1: Data Model
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-585 | Extends `ProjectSetupJob` with `command` discriminator | Yes (V. Database) | Leaner schema, single table, nullable retro-spec columns |
| AIB-587 | Creates new `SpecGenerationJob` model + `specsGeneratedAt` on Project | Yes (V. Database) | Cleaner separation, but duplicates status endpoint logic |

**Best**: AIB-585 — Single-table approach avoids code duplication. The spec itself suggested reusing `ProjectSetupJob` with a command discriminator.

### Decision Point 2: API Surface
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-585 | Extends existing `/setup/jobs` route with `command` param | Yes | Single API, query filter for command type |
| AIB-587 | New `/spec-generation/jobs` routes (separate POST + GET + PATCH) | Yes | Full independence, but ~350 lines of duplicated status handler |

**Best**: AIB-585 — DRY principle. The separate status endpoint in AIB-587 is a near-copy of the existing setup job status handler.

### Decision Point 3: Spec Status Tracking
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-585 | Server-side query for completed RETRO_SPEC job in board page | Yes | Accurate per-request, no schema addition |
| AIB-587 | `specsGeneratedAt` timestamp on Project model | Yes | More explicit, queryable, but requires migration |

**Best**: AIB-587 — Explicit timestamp on Project is more ergonomic for queries. However, AIB-585's approach is functionally equivalent.

### Decision Point 4: SSR Safety for localStorage
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-585 | `useSyncExternalStore` for localStorage read | Yes (I. TypeScript) | SSR-safe, React 18 pattern |
| AIB-587 | Direct `localStorage` in `useEffect` | Yes | Works but less idiomatic |

**Best**: AIB-585 — `useSyncExternalStore` is the correct React 18 pattern for external stores.

### Decision Point 5: Depth Type Safety
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-585 | `depth` as `String? @db.VarChar(20)` on ProjectSetupJob | Partial | Flexible but no DB-level constraint |
| AIB-587 | `SpecDepth` Prisma enum (`QUICK`, `STANDARD`, `COMPREHENSIVE`) | Yes (I. TypeScript) | Full type safety at DB and TS level |

**Best**: AIB-587 — Prisma enum provides compile-time and database-level type safety.

## Ranking & Recommendation

### 1. **AIB-585** - Best code (score: 86%)
**Why it wins**:
- Leaner architecture: extends existing model and API routes instead of duplicating
- Better constitution compliance: semantic `text-destructive` colors, modal test coverage
- `useSyncExternalStore` for SSR-safe localStorage (correct React 18 pattern)
- Zod `.refine()` for conditional validation (depth required when command=RETRO_SPEC)
- ~700 fewer lines of code for equivalent functionality

**Gaps to address**:
- Missing setup page redirect (US3) — should be added before ship

### 2. **AIB-587** - (score: 83%)
**Why it lost**:
- Duplicates entire job status endpoint logic (~134 lines copy of existing handler)
- Uses `text-ctp-red` for semantic error states instead of `text-destructive`
- Missing modal component test
- Larger API surface with separate `/spec-generation/` routes adds maintenance burden
- More total code (+44% lines) without proportional feature benefit

**Strengths worth cherry-picking**:
- Setup page Step 2 flow with redirect
- `SpecDepth` Prisma enum for type safety
- `specsGeneratedAt` on Project model
