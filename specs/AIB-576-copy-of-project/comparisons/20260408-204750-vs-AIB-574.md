## Implementation Choices Analysis

### [Spec] Route unconfigured projects to setup (FR-001)
| Ticket | Approach |
|--------|----------|
| AIB-576 | Board page checks `isSetupRequired()` and redirects; new entry page `/projects/[id]` routes to setup or board; project card links to entry page |
| AIB-574 | Setup page exists but no board page redirect; users must navigate to `/setup` manually |

**Best**: AIB-576 - Complete routing ensures no dead-end pages.

### [Spec] Credential verification (FR-005)
| Ticket | Approach |
|--------|----------|
| AIB-576 | Server-side `getOwnerCredentialReadiness()` per agent, included in setup API response |
| AIB-574 | Client-side fetch to `/api/credentials` with client-side provider mapping |

**Best**: AIB-576 - Server-side validation is more secure and avoids an extra client round-trip.

### [Spec] Attempt history preservation (FR-017)
| Ticket | Approach |
|--------|----------|
| AIB-576 | `ProjectSetupAttempt` model with explicit `attemptNumber` field for ordered history |
| AIB-574 | `ProjectSetupJob` model without attempt numbering; relies on `createdAt` ordering |

**Best**: AIB-576 - Explicit numbering matches spec's auditability requirement.

### Decision Point 1: Domain Module Architecture
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-576 | Dedicated `lib/project-setup/` module (service, state, types, workflow-dispatch) | Yes (II. Component-Driven) | Clean separation, testable units |
| AIB-574 | Logic embedded in route handlers (219-line route.ts, 107-line status route) | Partial | Simpler structure, but harder to test |

**Best**: AIB-576 - Proper domain separation per constitution Principle II.

### Decision Point 2: Component Structure
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-576 | 3 focused components: `ProjectSetupPage` (131), `ProjectSetupStartForm` (146), `ProjectSetupStatus` (131) | Yes (II) | Each handles one concern |
| AIB-574 | Single `SetupPageClient` component (262 lines) with all states inline | No | Simpler file structure, but violates single responsibility |

**Best**: AIB-576 - Constitution requires composable components with single responsibility.

### Decision Point 3: State Derivation
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-576 | Pure function `deriveProjectSetupState()` in `state.ts`, reused across server pages and API | Yes (I. TypeScript-First) | Testable, reusable |
| AIB-574 | `deriveSetupState()` defined inside route handler | Partial | Less reusable |

**Best**: AIB-576 - Pure functions in shared modules enable better testing.

### Decision Point 4: Workflow Security
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-576 | Workflow uses env secrets (APP_URL, WORKFLOW_API_TOKEN); only project/attempt IDs passed as inputs | Yes (IV. Security-First) | Secrets stay in env |
| AIB-574 | Passes `callbackUrl` and `workflowToken` as workflow dispatch inputs | No | Secrets visible in workflow run logs |

**Best**: AIB-576 - Passing secrets as inputs violates Security-First principle.

## Ranking & Recommendation

### 1. **AIB-576** - Best code (score: 92%)
**Why it wins**:
- Complete board-to-setup routing (no dead-end pages)
- Proper domain module architecture (`lib/project-setup/`)
- Server-side credential validation (security + fewer round-trips)
- 3 focused components vs 1 monolithic component
- Pure state derivation functions, reusable across server/client
- Workflow secrets stay in environment (not passed as inputs)
- Explicit attempt numbering for audit trail
- 9 test files with comprehensive integration + unit + component coverage
- 3x cheaper ($8.04 vs $23.27) - informational only

### 2. **AIB-574** - (score: 75%)
**Why it lost**:
- No board page redirect for unconfigured projects
- Monolithic 262-line client component violates Component-Driven principle
- Client-side credential check (extra round-trip, less secure)
- Passes workflow secrets as dispatch inputs (security concern)
- No explicit attempt numbering
- Less comprehensive test coverage (4 files vs 9)
