## Implementation Choices Analysis

### [Spec] Day boundary in user's local timezone (FR-004, FR-023 spirit)
| Ticket | Approach |
|--------|----------|
| AIB-688 | IANA `timezone` threaded through server query; `Intl.DateTimeFormat('en-CA', {timeZone})` bucketing with `dayKeyToUtcStart` helper |
| AIB-675 | UTC-only formatting (`timeZone: 'UTC'` in date formatting) |
| AIB-680 | UTC-only date keys built from `cursor.getFullYear()/getMonth()/getDate()` |
| AIB-681 | UTC period bounds via `Date.UTC(...)`; no per-viewer timezone |
| AIB-683 | N/A (off-topic) |

## Ranking & Recommendation

### 1. **AIB-688** — score ~88%
**Why it wins**:
- Only implementation honoring the spec's local-timezone decision (FR-004 spirit, SC-002 accuracy)
- Modular component split matches shadcn conventions; centralized query-keys
- Only ticket with Zod validation at the API boundary
- Only ticket with an E2E test covering the no-spinner-flash requirement (SC-001)

### 2. **AIB-681** — score ~74%
**Why it lost**: No local-timezone handling (UTC only); no Zod; agent filter visibility rule is approximate; no E2E.

### 3. **AIB-675** — score ~72%
**Why it lost**: UTC-only; monolithic 355-line component; no Zod; no E2E. Good test count, but doesn't offset missed spec fundamentals.

### 4. **AIB-680** — score ~58%
**Why it lost**: Monolithic component, UTC-only, thin test coverage (2 files), no Zod, intensity thresholds not quartile-based.

### 5. **AIB-683** — score ~10%
**Why it lost**: Implements an unrelated auto-mode workflow — does not address the activity-heatmap spec at all. Included only for completeness as requested.
