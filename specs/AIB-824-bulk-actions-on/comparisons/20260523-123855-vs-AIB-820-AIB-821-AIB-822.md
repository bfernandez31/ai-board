## Implementation Choices Analysis

### [Spec] FR-010 — Atomic bulk actions
| Ticket | Approach |
|--------|----------|
| AIB-824 | `prisma.$transaction` + `getBulkInboxTicketLookup` returns `ok:false` → 409 `BULK_ACTION_BLOCKED` if **any** ticket is ineligible; nothing mutates. True all-or-nothing. |
| AIB-820 | Explicit "best-effort" `Promise.allSettled` in `lib/tickets/bulk.ts` with `BulkSkipReason` (`NOT_FOUND`, `NOT_IN_INBOX`, `VERSION_CONFLICT`, `ACTIVE_JOB`, …). Partial success by design — peer failures do not abort siblings. Direct violation of FR-010. |
| AIB-821 | `assertInboxAndProject` + `detectVersionMismatch` short-circuit with 409 `BULK_CONFLICT_STAGE_DRIFT` / `BULK_CONFLICT_VERSION` if any ticket fails preconditions. Atomic delete/merge inside `prisma.$transaction`. |
| AIB-822 | `lib/tickets/bulk-update.ts` issues per-ticket `updateMany` calls via `Promise.all` and returns `{succeeded, skipped}`; deletion returns `{succeeded, skipped}` too. Partial success — violates FR-010. |

**Best**: AIB-821 / AIB-824 — both correctly implement the conservative all-or-nothing decision recorded in the spec.

### [Spec] FR-004 — Range selection helper
| Ticket | Approach |
|--------|----------|
| AIB-824 | Range logic inlined into `board.tsx`/`ticket-card.tsx`; harder to unit-test independently. |
| AIB-820 | Pure helper `computeRangeSelection` in `lib/board/selection.ts` (153-line dedicated test). Best separation. |
| AIB-821 | `use-bulk-selection.ts` hook + matching unit test; clean React-idiomatic split. |
| AIB-822 | `use-ticket-selection.ts` hook (109-line test) — similar pattern to AIB-821. |

**Best**: AIB-820 — pure function is the most testable and reusable; AIB-821/822 close behind with hook-based extraction.

### Decision Point 1 — API surface (routes per action vs. single endpoint)
| Ticket | Approach | Trade-offs |
|--------|----------|------------|
| AIB-824 | 4 distinct routes (`/bulk/{agent,delete,merge,model-config}`) | RESTful, each route can evolve independently |
| AIB-820 | 4 distinct routes (`/bulk/{agent,delete,fusion,model}`) | Same; uses bespoke "Fusion" naming that diverges from spec wording ("Merge") |
| AIB-821 | 4 distinct routes (`/bulk/{agent,delete,merge,model}`) + structured action logging | Same + best operational observability |
| AIB-822 | **Single** `/bulk` route with discriminator `action: 'delete'|'merge'|'update-agent'|'update-model'` | Smaller surface but less granular auth/logging; bigger switch with mixed concerns |

**Best**: AIB-821 — RESTful split + per-action logs (`[bulk-action] start … done …`).

### Decision Point 2 — Optimistic concurrency
| Ticket | Approach | Constitution V (DB Integrity) |
|--------|----------|------------------------------|
| AIB-824 | INBOX/stage precheck inside transaction; no explicit row-version check | Partial |
| AIB-820 | `TicketRef = {id, version}` everywhere; explicit per-row version comparison | Yes |
| AIB-821 | `expectedVersions: Record<string, number>` validated via `detectVersionMismatch` → 409 `BULK_CONFLICT_VERSION` | Yes |
| AIB-822 | `updateMany` with `where: { version }` per ticket; no client-supplied expected version | Partial |

**Best**: AIB-820 / AIB-821 — both carry expected versions through the wire format, giving the UI a clean conflict-resolution surface.

### Decision Point 3 — Notifications / side-effect awareness
| Ticket | Approach |

**Best**: AIB-821 — only implementation that surfaces bulk side-effects to affected users. Considerate, fully migrated, and atomically applied.

## Ranking & Recommendation

### 1. **AIB-821** — Best code (score: 91%)
**Why it wins**:
- Only implementation that satisfies BOTH FR-010 atomicity AND surfaces side-effects via a notification migration done correctly (TICKET_DELETED / TICKET_MERGED with `SetNull` preserving source key snapshots).
- Strongest optimistic concurrency: client supplies `expectedVersions`, server returns `BULK_CONFLICT_VERSION` with `currentVersions` map → UI can resolve without a full refetch.
- Cleanest operational story: structured `[bulk-action] start/done` logging on every route.
- Highest test density (39%) and uniquely covers the bulk notification path.

### 2. **AIB-820** — (score: 84%)
**Why it lost**:
- Explicitly best-effort (`Promise.allSettled` + `BulkSkipReason`) — directly contradicts the spec's conservative "all-or-nothing" decision (Auto-Resolved Decisions §3).
- Otherwise the most architecturally clean entry: pure `computeRangeSelection` helper, strong cross-field Zod refinements, dedicated `lib/board/selection.ts`.
- "Fusion" terminology diverges from spec wording ("Merge"), which is a small UX/copy regression.

### 3. **AIB-824 (source)** — (score: 82%)
**Why it lost**:
- Atomic semantics ✓ but lacks row-version optimistic concurrency on bulk paths.
- Range-selection logic is inlined in `board.tsx` rather than extracted to a testable helper.
- Mixes new bulk DB helpers into the already-large `lib/db/tickets.ts` (+346 lines).
- Lower test ratio (33%) and no observability hooks for bulk actions.

### 4. **AIB-822** — (score: 76%)
**Why it lost**:
- Allows partial success (`{succeeded, skipped}`) on bulk-update **and** delete — violates FR-010.
- Per-ticket `Promise.all` of `updateMany` calls is not wrapped in a transaction → race window between findMany and the parallel updates.
- Single `/bulk` endpoint mixes four conceptually distinct actions in one switch, complicating per-action auth/logging.
- Cleanest test ratio (47%) of the four, but covers a less rigorous implementation.
