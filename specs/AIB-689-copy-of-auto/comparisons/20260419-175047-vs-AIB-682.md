## Implementation Choices Analysis

### [Spec] Running-job guard on enable
| Ticket | Approach |
|--------|----------|
| AIB-689 | Client reads `hasRunningWorkflowJob` from cached job state and chooses whether to pass `immediateDispatchStage`. Two HTTP calls: PATCH `/tickets/:id` + POST `/transition`. |
| AIB-682 | Server queries `Job` for PENDING/RUNNING non-`comment-*` rows inside `enableAutoMode` and only dispatches when none found. Single HTTP call to `/auto-mode`. |

**Best**: AIB-682 — atomic server-side check eliminates TOCTOU race between client snapshot and dispatch.

### Decision Point 1: API surface
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-689 | Reuses generic PATCH `/tickets/:id` with `{autoMode, version}`; separate POST `/transition` | Partial | Simpler surface, but no input validation dedicated to autoMode payload; two requests per toggle. |
| AIB-682 | Dedicated PATCH `/api/projects/[projectId]/tickets/[id]/auto-mode` with Zod `{enabled: boolean}` | Yes | Clear endpoint boundary, validated input per §IV Security-First. |

**Best**: AIB-682 — dedicated endpoint + Zod validation aligns with security principle.

### Decision Point 2: Next-stage resolution
| Ticket | Approach |
|--------|----------|
| AIB-689 | Hardcodes `NEXT_AUTO_STAGE` map in `lib/tickets/auto-transition.ts` AND `IMMEDIATE_DISPATCH_NEXT` map in `ticket-card.tsx` AND `CHAIN_BY_STAGE` in the modal (three copies). |
| AIB-682 | Reuses existing `getNextStage` from `@/lib/stage-transitions` server-side; dedicated `computeChainedStages` util for UI preview. |

**Best**: AIB-682 — single source of truth, reuses existing transition logic.

### Decision Point 3: Client cache strategy
| Ticket | Approach |
|--------|----------|
| AIB-689 | Invalidates queries on success only; no optimistic UI. |
| AIB-682 | Optimistic update with rollback on error; invalidates on success. |

**Best**: AIB-682 — instant UI feedback matches the TanStack Query patterns used elsewhere in the codebase.

### Decision Point 4: Stage-preview helper
| Ticket | Approach |
|--------|----------|
| AIB-689 | `getAutoTransitionChain` exported from the modal file itself. |
| AIB-682 | Pure util `computeChainedStages` in `lib/utils/auto-mode-stage-preview.ts`, dedicated unit tests. |

**Best**: AIB-682 — pure function in utils folder is easier to unit-test and reuse.

## Ranking & Recommendation

### 1. **AIB-682** — Best code (score: 93%)
**Why it wins**:
- Server-side atomic enable+dispatch eliminates client/server race on running-job check.
- Dedicated PATCH endpoint validated with Zod per Security-First principle.
- Reuses existing `getNextStage` instead of duplicating stage-chain maps.
- Optimistic-update mutation matches project TanStack Query patterns.
- Test pyramid: unit + integration (`auto-mode-hook.test.ts`, `auto-mode.test.ts`, `transitions.test.ts`) + E2E (`auto-mode.spec.ts`).

### 2. **AIB-689** (source) — (score: 80%)
**Why it lost**:
- Running-job check lives in the client cache → possible TOCTOU if cache is stale.
- Two-request toggle flow (PATCH + POST transition) can leave `autoMode=true` with no dispatch on transient network failures (self-heals via next job hook, but still an inconsistent interim state).
- Stage-chain mapping duplicated in three files.
- Tests are unit-only; no integration or E2E coverage of the chain.
- Uses generic ticket PATCH instead of a dedicated validated endpoint.
