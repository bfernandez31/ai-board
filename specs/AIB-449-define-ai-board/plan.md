# Implementation Plan: Define .ai-board/config.yml Schema and Validation

**Branch**: `AIB-449-define-ai-board` | **Date**: 2026-04-01 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/AIB-449-define-ai-board/spec.md`

## Summary

Define a versioned YAML schema for `.ai-board/config.yml` that external projects use to declare their environment, tooling, and workflow configuration. Implement a Zod-based validation utility that parses the YAML file, validates all fields, collects errors/warnings, and returns a fully typed `ProjectConfig` object with defaults populated.

## Implementation Outline

### Step 1: Add YAML Dependency

- `bun add yaml`
- Verify TypeScript types resolve correctly

### Step 2: Define Zod Schemas (`lib/validations/config.ts`)

- Define enum schemas: `ProjectLanguageSchema`, `ProjectFrameworkSchema`, `PackageManagerSchema`, `ServiceTypeSchema`, `AgentCliSchema`
- Define section schemas: `ProjectSectionSchema`, `RuntimeSectionSchema`, `CommandsSectionSchema`, `ServiceConfigSchema`, `AgentSectionSchema`
- Define root `ProjectConfigSchema` with `.passthrough()` for unknown field detection
- Export `validateConfig()` function that:
  1. Runs `safeParse()` on input
  2. Collects unknown field warnings via key diff
  3. Maps Zod errors to `ValidationError` format (path, type, value, message)
  4. Returns `ValidationResult` discriminated union
- Export inferred types via `z.infer<>`

### Step 3: Implement Config Loader (`lib/config-loader.ts`)

- `loadConfig(projectDir: string)`: async function that:
  1. Resolves path to `{projectDir}/.ai-board/config.yml`
  2. Checks file existence — returns specific FR-010 error if missing
  3. Reads and parses YAML with `yaml.parse()` — catches syntax errors with line info
  4. Delegates to `validateConfig()` from Step 2
  5. Returns `ValidationResult`

### Step 4: Write Unit Tests (`tests/unit/config-schema.test.ts`)

Tests for `validateConfig()`:
- Valid config with all fields → success, correct types
- Valid config with only required fields → success, defaults populated
- Missing required fields → errors with correct paths and types
- Invalid enum values → errors listing allowed values
- Wrong types (number instead of string) → type errors
- Multiple errors collected in single pass
- Unknown fields produce warnings (not errors)
- Empty object → all required field errors returned
- Version validation: `1` passes, `2` fails, `"one"` fails

### Step 5: Write Unit Tests (`tests/unit/config-loader.test.ts`)

Tests for `loadConfig()`:
- Missing file → specific "Missing .ai-board/config.yml" error
- Invalid YAML syntax → parse error with guidance
- Valid file → delegates to schema validation correctly
- Empty file → treated as missing all required fields

## Testing Strategy

| User Story | Test Type | Location | Rationale |
|------------|-----------|----------|-----------|
| US-1: Valid config parsing | Unit | `tests/unit/config-schema.test.ts` | Pure function, no side effects |
| US-2: Invalid config errors | Unit | `tests/unit/config-schema.test.ts` | Pure function, validation logic |
| US-3: Missing config detection | Unit | `tests/unit/config-loader.test.ts` | File I/O with mocked fs |
| US-4: Optional commands skipped | Unit | `tests/unit/config-schema.test.ts` | Pure function, default behavior |
| US-5: Schema version validation | Unit | `tests/unit/config-schema.test.ts` | Pure function, enum check |
| Edge cases (YAML syntax, etc.) | Unit | `tests/unit/config-loader.test.ts` | Parser error handling |

**Decision tree applied**: All user stories involve pure functions or simple file I/O → **Vitest unit tests**. No database, no React components, no browser required.

## Risks & Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| YAML parser edge cases (anchors, tags) | Config fails to parse | Use `yaml` library defaults which handle standard YAML; document unsupported features |
| Zod v4 error format changes | Error mapping breaks | Pin Zod version; test error output format explicitly |
| Future schema versions (v2+) | Versioned validation needed | Design with version check upfront (FR-011); new versions add new schema branches |
