## Implementation Choices Analysis

### [Spec] Concurrency control on bulk update / delete
| Ticket | Approach |
|--------|----------|
| AIB-822 | `version: { increment: 1 }` without precondition — last write wins; concurrent edits silently overwritten. |
| AIB-820 | Re-reads versions before update; classifies errors into `BulkSkipReason` enum (`VERSION_CONFLICT`, `ACTIVE_JOB`, …). |
| AIB-821 | Accepts `expectedVersions` from client and rejects with `BULK_CONFLICT_STAGE_DRIFT` (409) or per-row version mismatch — true optimistic locking matching the spec assumption. |

**Best**: **AIB-821** — closest to spec assumption that "the existing optimistic concurrency control (version field) is used to detect concurrent modifications."

### [Spec] Attachment limit during merge (FR-015)
| Ticket | Approach |
|--------|----------|
| AIB-822 | Server accepts `selectedAttachments: string[]` — picker UI not implemented. |
| AIB-820 | Auto-clips beyond 5 with banner; no user selection. |
| AIB-821 | Just shows combined count, no enforcement. |

**Best**: **None fully implement it** — AIB-822 lays the data path; AIB-820 is most user-visible; AIB-821 is weakest here.

### Decision Point 1: API shape
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-822 | Single `POST /tickets/bulk` with `action` discriminator | OK | Compact, but one giant Zod union; harder to evolve per-action |
| AIB-820 | 4 routes (`/delete`, `/agent`, `/model`, `/fusion`) | OK | Cleaner separation, easier auth/rate-limit per action |
| AIB-821 | 4 routes (`/delete`, `/agent`, `/model`, `/merge`) + named errors | OK | Same as AIB-820, plus per-route `BulkConflictError` shape |

**Best**: **AIB-821** (REST-style + structured error class).

### Decision Point 2: Merge naming
- AIB-822/AIB-821 use **"Merge"** (matches spec wording).
- AIB-820 uses **"Fusion"** (anchor/absorbed) — diverges from spec terminology and would require renaming consolidated docs.

**Best**: **AIB-821/AIB-822** — spec-aligned.

### Decision Point 3: Schema / DB
- AIB-822: No migration; relies on existing `version` field.
- AIB-820: No migration; adds notification side-effects only.
- AIB-821: Adds `prisma/migrations/20260522063559_bulk_actions_inbox/migration.sql` to support cascading notification updates and audit trail.

**Best**: **AIB-821** — only ticket that touches schema deliberately.

### Decision Point 4: Test coverage
- AIB-822: 6 tests, no E2E.
- AIB-820: 9 tests, no E2E.
- AIB-821: 12 tests including `tests/e2e/inbox-bulk-operations.spec.ts`, integration coverage for constraints, merge, agent, model, delete, and notifications.

**Best**: **AIB-821**.

## Ranking & Recommendation

### 1. **AIB-821** — Best (score: 92%)
**Why it wins**:
- Optimistic concurrency with `expectedVersions` matches the spec's stated assumption.
- Atomic `prisma.$transaction` for merge + bulk delete; stage-drift detection (`BULK_CONFLICT_STAGE_DRIFT`).
- Highest test coverage (E2E + integration + unit).
- Ships a Prisma migration alongside the code.
- REST-style API with structured error class.

### 2. **AIB-820** — (score: 86%)
**Why it lost**:
- "Fusion" terminology diverges from spec.
- No optimistic-version client contract (server re-reads but doesn't accept `expectedVersions`).
- No E2E test.
- Selects an auto-clip strategy for attachments rather than asking the user.

### 3. **AIB-822** (source) — (score: 78%)
**Why it lost**:
- Single bulk endpoint with `action` switch — workable but harder to evolve and audit per action.
- Bulk update/delete don't verify version → silent overwrite of concurrent edits (FR-010, FR-020 only partial).
- 6 tests, no E2E.
- Smallest surface area but also weakest on durability guarantees.
