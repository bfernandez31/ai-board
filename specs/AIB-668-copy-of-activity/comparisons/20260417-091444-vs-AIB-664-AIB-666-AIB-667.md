## Implementation Choices Analysis

### Decision Point 1: API Route Namespace
| Ticket | Approach |
|--------|----------|
| AIB-668 | `/api/user/activity-heatmap` — scoped to user |
| AIB-664 | `/api/heatmap` — shortest, least scoped |
| AIB-666 | `/api/activity-heatmap` — flat |
| AIB-667 | `/api/activity/heatmap` — grouped by feature |

**Best**: AIB-668 / AIB-667 — clearer namespace avoids future collisions.

### Decision Point 2: Component Structure
| Ticket | Approach |
|--------|----------|
| AIB-668 | Single `activity-heatmap.tsx` file |
| AIB-664 | Single `activity-heatmap.tsx` file |
| AIB-666 | Single `activity-heatmap.tsx` file |
| AIB-667 | 6 components (cell/grid/filters/legend/counter) + `use-activity-heatmap` hook |

**Best**: AIB-667 — modular split is most idiomatic for scale and testability.

### Decision Point 3: Intensity Thresholds
| Ticket | Approach |
|--------|----------|
| AIB-668 | Quartile-based (adapts to user volume) |
| AIB-664 | Quartile-based (adapts to user volume) |
| AIB-666 | Ratio-based (max/4 buckets) |
| AIB-667 | Hardcoded (1 / 3 / 7 jobs) |

**Best**: AIB-668 / AIB-664 — quartile is the most defensible against skewed distributions.

### Decision Point 4: Timezone Handling
| Ticket | Approach |
|--------|----------|
| AIB-668 | Server-local bucketing |
| AIB-664 | Server-local bucketing |
| AIB-666 | Server-local bucketing + uses `startedAt` (divergent) |
| AIB-667 | Accepts `tz` param; validates via `Intl.DateTimeFormat`; buckets on `completedAt` in user tz |

**Best**: AIB-667 — only implementation that handles users outside UTC correctly.

### Decision Point 5: URL Query Params
| Ticket | Approach |
|--------|----------|
| AIB-668 | `heatmapPeriod` / `heatmapAgent` (prefixed, safe) |
| AIB-664 | `period` / `agent` (risks collision on /projects) |
| AIB-666 | Prefixed, but uses `year-YYYY` format (spec divergence) |
| AIB-667 | `year` / `agent` |

**Best**: AIB-668 — safest namespacing, matches spec format.

## Ranking & Recommendation

### 1. **AIB-667** — Best overall (89%)
**Why it wins**:
- Only implementation with correct timezone handling (crucial for non-UTC users).
- Most modular architecture (6 components + custom hook) — easiest to extend and test.
- Aurora B+ theme compliance with `aurora-cell-*` utilities.
- Zod validation + strong test suite (40 tests).

**Weaknesses**: Tooltip always shows "tickets shipped" even at 0; day labels not sticky on mobile; hardcoded intensity thresholds.

### 2. **AIB-668** (source) — 86%
**Why it competes**:
- Cleanest single-file implementation with **every** acceptance criterion met.
- Only ticket with the correct `length > 2` agent-filter rule and conditional tooltip omission.
- Proper Aurora theming and safe URL param namespacing.
- Smallest, focused diff (+1,523).

**Weaknesses**: Smaller test suite (23) with no integration-test depth for queries; monolithic component.

### 3. **AIB-664** — 87%
**Why it lost**:
- Most rigorous engineering: 51 tests, reusable `getAccessibleProjectIdsForUser` helper, rich JSDoc.
- Drops Aurora theme (uses plain `bg-violet-500` shades).
- Mildly incorrect agent-filter hide rule (`length > 0`) and uses unprefixed `period`/`agent` query params (collision risk).

### 4. **AIB-666** — 69%
**Why it lost**:
- Diverges from spec: `year-YYYY` period format, `startedAt` bucketing (others use `completedAt`).
- No Zod validation on API route.
- No integration tests.
- Aurora theme only partial.
