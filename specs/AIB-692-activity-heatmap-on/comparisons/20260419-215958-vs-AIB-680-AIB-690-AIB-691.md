## Implementation Choices Analysis

### [Spec] FR-003/Decision 4: Intensity threshold calculation (quantile vs max-ratio)

| Ticket | Approach |
|--------|----------|
| AIB-692 | `computeQuantileThresholds` with p25/p50/p75/p90 on non-zero daily counts; collapses to mid-bucket when all counts equal |
| AIB-680 | `getIntensityLevel(count, max)` uses `ratio = count / max` buckets (0.25/0.5/0.75) — fails spec |
| AIB-690 | `computeQuantileBuckets` with p25/p50/p75; explicit empty-input handling — best quantile implementation |
| AIB-691 | `computeLevel(count, max)` uses `ratio = count / max` — same issue as AIB-680 |

**Best**: AIB-692 and AIB-690 — both correctly implement quantile-based thresholds as the spec requires. Max-ratio bucketing (AIB-680, AIB-691) violates Decision 4 because it produces uniformly-light displays for low-activity users.

### [Spec] Decision 5: URL query parameter naming

| Ticket | Params |
|--------|--------|
| AIB-692 | `?year=2025&agent=claude` (matches spec exactly) |
| AIB-680 | `?period=2025&agent=CLAUDE` (wrong: spec says `year`) |
| AIB-690 | `?heatmapPeriod=2025&heatmapAgent=CLAUDE` (wrong: verbose, not in spec) |
| AIB-691 | `?heatmapPeriod=2025&heatmapAgent=CLAUDE` (wrong: same as 690) |

**Best**: AIB-692 — the only ticket to honor the explicit Decision 5 param naming.

### Decision Point: Type system design

| Ticket | Approach |
|--------|----------|
| AIB-692 | String-based period (`'rolling'` \| `'YYYY'`) with runtime validation; simple and matches spec's URL design |
| AIB-680 | String period (`'last-12-months'` \| `'YYYY'`); moderate types |
| AIB-690 | Discriminated union `{ kind: 'year' \| 'rolling12m' }` — most type-safe but over-engineered for spec needs |
| AIB-691 | Union type `'last12' \| number` — elegant, most TypeScript-idiomatic |

**Best on type safety alone**: AIB-690/AIB-691. **Best for spec alignment**: AIB-692.

### Decision Point: Date handling (timezone safety)

| Ticket | Approach |
|--------|----------|
| AIB-692 | Uses local-date constructors (`new Date(y, m, d)`); vulnerable to server-side timezone drift |
| AIB-680 | Mixed local/UTC — inconsistent |
| AIB-690 | All `Date.UTC(...)` with `formatUTCDate`; deterministic across timezones ✓ |
| AIB-691 | All `Date.UTC(...)` with `formatUtcDate`; deterministic ✓ |

**Best**: AIB-690 and AIB-691 — UTC-safe handling.

## Ranking & Recommendation

### 1. **AIB-692** (source) — Score: **85%**
**Why it wins**:
- Only ticket to implement both explicit spec decisions correctly: quantile thresholds (FR-003/Decision 4) AND `year`/`agent` URL param names (Decision 5).
- Zod-validated API route with proper 400/401/500 branches.
- Compact but complete implementation (1314 lines of code + 608 lines of tests).
- Clean, task-focused type system that exactly models what the spec describes.

**Weaknesses**:
- Local-date handling (not UTC) — minor risk for timezone drift.
- Single monolithic component vs AIB-690's split.

### 2. **AIB-690** — Score: **84%**
**Why it came second**:
- Highest code quality: discriminated unions, UTC-safe dates, best component split, most test coverage.
- BUT uses `heatmapPeriod`/`heatmapAgent` param names, violating Decision 5.
- Over-engineered for the spec: 2317 lines, 2× the cost ($35.54) of the source.

### 3. **AIB-691** — Score: **74%**
**Why it lost**:
- Uses max-ratio bucketing (`count / max`) instead of quantiles — violates FR-003/Decision 4.
- Wrong URL param names.
- Otherwise clean: UTC-safe dates, elegant `'last12' | number` union, modular `grid.ts`.

### 4. **AIB-680** — Score: **70%**
**Why it lost**:
- Uses max-ratio bucketing — same FR-003 violation as AIB-691.
- URL param `period` instead of `year`.
- Single 401-line component is hardest to test in isolation.
- No dedicated aggregation unit tests.
