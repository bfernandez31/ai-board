## Implementation Choices Analysis

### [Spec] AC3: Removal of batch Gemini code
| Ticket | Approach |
|--------|----------|
| AIB-631 | Removes `agent` field from batch schema entirely, removes `usageSnapshotMode` |
| AIB-629 | Removes `agent` field from batch schema entirely, removes `usageSnapshotMode` |
| AIB-630 | Narrows `agent` to `['MISTRAL']`, adds 400 rejection for Gemini batch, retains `mergeTelemetryValue` with CUMULATIVE mode |

**Best**: AIB-630 - Migration-safe: explicitly rejects old Gemini batch payloads with a clear error message rather than silently accepting/ignoring them.

### [Spec] AC6: Failure path handling
| Ticket | Approach |
|--------|----------|
| AIB-631 | MALFORMED_TELEMETRY console.warn for missing model / invalid tokens, `continue` to skip |
| AIB-629 | Tests for null metrics retention and missing job_id warning |
| AIB-630 | MALFORMED_TELEMETRY warning in server code + tests for FAILED status with partial telemetry + duration backfill when telemetry missing |

**Best**: AIB-630 - Most comprehensive failure coverage: server-side resilience plus integration tests verifying failure behavior end-to-end.

### Decision Point 1: OTLP Attribute Naming
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-631 | Prefixed: `gemini_cli.usage.input_tokens`, `gemini_cli.model` | Yes | More explicit but assumes specific Gemini CLI attribute format |
| AIB-629 | Simple: `input_tokens`, `output_tokens`, `model` | Yes | Consistent with Claude/Codex patterns; simpler |
| AIB-630 | Multi-key fallback via `findFirstAttribute` with 5+ alternate keys per metric | Yes | Most resilient but speculative over-engineering |

**Best**: AIB-629 - Simplest approach consistent with existing provider patterns. The event name `gemini_cli.api_response` already scopes the attributes; prefixing is redundant.

### Decision Point 2: Merge Mode Architecture
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-631 | Removes CUMULATIVE entirely; all metrics use DELTA (summation) | Yes | Simplest but may double-count if Gemini emits cumulative snapshots |
| AIB-629 | Same as AIB-631: removes CUMULATIVE, always DELTA | Yes | Same trade-off |
| AIB-630 | Dual-track: `deltaMetrics` for Claude/Codex, `cumulativeMetrics` for Gemini (Math.max merge) | Yes | Handles both emission styles but adds complexity |

**Best**: AIB-630 - Correctly anticipates that Gemini CLI may emit cumulative snapshots (as the old batch code did). `Math.max` prevents double-counting.

### Decision Point 3: Shell-Side OTLP Configuration
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-631 | Minimal: just removes stream-json, no explicit OTEL env setup | Yes | Relies on Gemini CLI's default OTLP behavior |
| AIB-629 | Minimal: removes stream-json only | Yes | Same reliance on defaults |
| AIB-630 | Explicit `setup_gemini_telemetry()` function: sets `OTEL_LOGS_EXPORTER`, `OTEL_EXPORTER_OTLP_PROTOCOL`, batch params | Yes | Explicit configuration; doesn't depend on Gemini CLI defaults |

**Best**: AIB-630 - Explicit OTLP environment setup ensures telemetry works regardless of Gemini CLI's default configuration.

### Decision Point 4: Scope Discipline
| Ticket | Approach |
|--------|----------|
| AIB-631 | 14 source files: Gemini OTLP + dispatch consolidation + board.tsx refactor + transition.ts rewrite |
| AIB-629 | 2 source files: Gemini OTLP only |
| AIB-630 | 5 source files: Gemini OTLP + job status fix + OTLP schema utility |

**Best**: AIB-629 - Tightest scope. AIB-630 is also reasonable (new utility and bug fix are related). AIB-631's scope creep mixes unrelated refactoring with the feature, making review and rollback harder.

## Ranking & Recommendation

### 1. **AIB-630** - Best implementation (score: 87%)
**Why it wins**:
- Best test coverage: 4 test files including unit test, failure paths, and API surface verification (80% test ratio)
- Migration-safe: explicit 400 rejection for Gemini batch payloads with clear error message
- Proper dual-track merge (DELTA for Claude/Codex, CUMULATIVE for Gemini) handles real-world emission patterns
- Explicit shell-side OTLP configuration (`setup_gemini_telemetry()`) instead of relying on defaults
- Clean scope: only touches files relevant to the feature + related bug fix

### 2. **AIB-629** - Strong runner-up (score: 85%)
**Why it's close**:
- Cleanest, most focused implementation (2 source files only)
- Good failure path tests (T008a, T008b)
- Simple attribute naming consistent with existing patterns
**Why it lost**:
- Removes `agent` field from batch schema entirely (migration risk for Mistral)
- No unit tests for OTLP schema
- No job status or API surface tests
- Relies on Gemini CLI defaults for OTLP configuration

### 3. **AIB-631** - Scope creep penalty (score: 69%)
**Why it lost**:
- Significant scope creep: 14 source files, dispatch consolidation and board.tsx refactor bundled with Gemini telemetry
- Unsafe TypeScript casts (`as unknown as Record<string, string>`, `as Job`)
- Weakest test coverage (1 test file, 7% ratio, no failure path tests)
- Mixes unrelated refactoring with feature work, complicating review and rollback
