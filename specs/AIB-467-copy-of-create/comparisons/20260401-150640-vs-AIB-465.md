## Implementation Choices Analysis

### [Spec] Display name fallback chain (FR-003)
| Ticket | Approach |
|--------|----------|
| AIB-467 | `user.name \|\| githubUsername \|\| "Unknown"` — matches spec requirement |
| AIB-465 | `profile.name \|\| profile.email` — uses email instead of GitHub username |

**Best**: AIB-467 — Spec explicitly requires GitHub username as fallback, not email.

### [Spec] Aurora theme styling (FR-010)
| Ticket | Approach |
|--------|----------|
| AIB-467 | Uses `aurora-bg-subtle` class on header card, consistent with other settings pages |
| AIB-465 | Uses `bg-card` and `border-border` — standard but not aurora-themed |

**Best**: AIB-467 — Spec requires aurora theme styling per project conventions.

### [Spec] Responsive layout (FR-011)
| Ticket | Approach |
|--------|----------|
| AIB-467 | `sm:grid-cols-2` grid, `px-4 sm:px-6` responsive padding, max-w-4xl container |
| AIB-465 | Single column layout, max-w-4xl container, no responsive grid breakpoints |

**Best**: AIB-467 — Better use of available screen space on larger viewports.

### Decision Point 1: Component Architecture
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-467 | Single page component (149 lines) with inline ProfileSkeleton | Acceptable | Simpler, all logic visible in one file |
| AIB-465 | Extracted `ProfileInfo` component + page wrapper (52+104 lines) | Better §II | More reusable, testable independently |

**Best**: AIB-465 — Better component-driven architecture per Constitution §II.

### Decision Point 2: Loading State UX
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-467 | Skeleton loading with animated pulse placeholders | Better UX | Polished, matches modern patterns |
| AIB-465 | Text "Loading profile..." | Minimal | Simple but less polished |

**Best**: AIB-467 — Skeleton loading provides better perceived performance.

### Decision Point 3: Error Handling UI
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-467 | Shows skeleton indefinitely on error (no explicit error state) | Missing | Error not surfaced to user |
| AIB-465 | Explicit error boundary with destructive-themed error message | Better §IV | User sees actionable error |

**Best**: AIB-465 — Explicit error states are important for user experience.

### Decision Point 4: Test Coverage Strategy
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-467 | 3 files: navigation link test, profile page component test, integration API test (339 lines) | Thorough | Tests navigation ordering, UI rendering, and API |
| AIB-465 | 2 files: ProfileInfo component test, integration API test with subscription upsert (178 lines) | Adequate | Tests component + deeper integration scenario |

**Best**: AIB-467 — Additional navigation test verifies Profile appears before Billing in both menus.

### Decision Point 5: GitHub API Strategy
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-467 | `GET /user/{providerAccountId}` — fetches by ID | Specific | Works even if token is expired for public profiles |
| AIB-465 | `GET /user` — fetches authenticated user | Standard | Requires valid token, returns `html_url` directly |

**Best**: Tie — Both approaches are valid with different trade-offs.
