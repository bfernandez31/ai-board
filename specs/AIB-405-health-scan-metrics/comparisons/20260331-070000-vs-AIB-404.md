## Implementation Choices Analysis

### [Spec] FR-002: Tooltip on hover for metric icons
| Ticket | Approach |
|--------|----------|
| AIB-405 | Uses shadcn/ui `<Tooltip>` component with `TooltipTrigger` and `TooltipContent` — accessible, keyboard-navigable |
| AIB-404 | Uses HTML `title` attribute — browser-dependent, not accessible, inconsistent with project UI standards |

**Best**: AIB-405 — Uses project-standard shadcn Tooltip per constitution II (Component-Driven).

### Decision Point 1: Formatter Reuse vs New Module
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-405 | Reuses `formatAbbreviatedNumber`, `formatCost`, `formatDuration` from existing `lib/analytics/aggregations` | Yes | DRY, no new files |
| AIB-404 | Creates new `lib/health/format.ts` with 4 custom formatters | Acceptable | Duplicates existing utils, adds maintenance burden |

**Best**: AIB-405 — Avoids code duplication by reusing existing analytics formatters.

### Decision Point 2: API Response Shape
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-405 | Flat: `{ security: [], compliance: [], tests: [], specSync: [] }` at `/health/trends` | Yes | Simpler to consume, consistent with existing health response patterns |
| AIB-404 | Nested: `{ trends: { security: [], ... } }` at `/health/trend` | Yes | Extra nesting adds complexity without benefit |

**Best**: AIB-405 — Flat response is simpler and matches existing API patterns in the codebase.

### Decision Point 3: Trend Data Fetching Strategy
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-405 | Fetches at dashboard level, passes as props to card and drawer | Yes | Single fetch point, explicit data flow |
| AIB-404 | Fetches at dashboard AND independently inside drawer via `useHealthTrend` | Yes (TanStack deduplicates) | Implicit coupling, drawer depends on separate hook |

**Best**: AIB-405 — Props drilling is explicit and avoids hidden data dependencies.

### Decision Point 4: Component Architecture
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-405 | Inlines sparkline (LineChart) and area chart (AreaChart) in parent components | Yes | Fewer files, simple for small components |
| AIB-404 | Extracts `Sparkline` and `ModuleAreaChart` as separate components | Yes | Better reusability, but adds 2 files for ~90 lines total |

**Best**: Tie — Both are valid. AIB-404's separation is slightly more maintainable; AIB-405's inline approach is simpler.

### Decision Point 5: staleTime Configuration
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-405 | `staleTime: 5 * 60 * 1000` (5 minutes) | Yes | Balanced freshness, will refetch after 5 min |
| AIB-404 | `staleTime: Infinity` | Concerning | Data never refreshes unless component remounts; stale data risk |

**Best**: AIB-405 — 5-minute staleTime balances freshness with performance.

## Ranking & Recommendation

### 1. **AIB-405** - Best code (score: 95%)
**Why it wins**:
- Reuses existing formatters (DRY) instead of creating redundant format module
- Proper shadcn Tooltip for accessibility (WCAG AA)
- Superior test coverage (5 test files, 466 test lines vs 3 files, 263 lines)
- Flat API response shape matches existing patterns
- Explicit prop-based data flow for trend data
- Reasonable staleTime (5 min vs Infinity)

### 2. **AIB-404** - (score: 85%)
**Why it lost**:
- Uses HTML `title` instead of shadcn Tooltip (constitution violation)
- Creates redundant `lib/health/format.ts` when `lib/analytics/aggregations` already has equivalent functions
- `staleTime: Infinity` risks serving stale trend data
- Nested API response adds unnecessary complexity
- Lower test coverage (3 files vs 5)
**What it does well**:
- Clean component extraction (Sparkline, ModuleAreaChart)
- Good test quality in the tests it does have
- Slightly lower AI cost ($7.16 vs $12.11)
