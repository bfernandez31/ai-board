## Implementation Choices Analysis

### [Spec] Agent early exit detection (FR-012, FR-013)
| Ticket | Approach |
|--------|----------|
| AIB-535 | Updates 3 agent command .md files (REVIEW_QUALITY, SECURITY, SPEC_SYNC) with SKIPPED result JSON templates and early exit instructions |
| AIB-534 | No agent command changes — detection only in workflow consolidation step |

**Best**: AIB-535 — Fully implements spec requirement that each agent detects "nothing to evaluate" (Decision 3 in spec). AIB-534 misses this entirely.

### [Spec] skipReason propagation
| Ticket | Approach |
|--------|----------|
| AIB-535 | Adds `skipReason` to `HealthModuleStatus` type, `statusUpdateSchema` Zod schema, and API response; propagated from agent → workflow → API → UI |
| AIB-534 | No `skipReason` field — uses hardcoded "Nothing to evaluate" string in UI |

**Best**: AIB-535 — Dynamic skip reasons per scan type (e.g., "No qualifying PRs" vs "No spec files") vs generic string.

### [Spec] Dashboard SKIPPED visual treatment (FR-007)
| Ticket | Approach |
|--------|----------|
| AIB-535 | Module card shows "N/A" badge for SKIPPED, displays `skipReason` text |
| AIB-534 | Module card shows previous score + "Skipped" badge side-by-side; also updates drawer-history and drawer-states components |

**Best**: AIB-534 — More comprehensive UI coverage (drawer components) and better UX showing previous score alongside skip indicator, matching spec Decision 2 ("show the last COMPLETED score alongside the Skipped indicator").

### Decision Point 1: API Query Strategy for SKIPPED Scans
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-535 | Dual-query: separate `latestCompletedScans` + `latestTerminalScans` queries with helper functions `getSkipReason()` and `getEffectiveScanStatus()` | Yes | Clear separation of concerns; 2 DB queries |
| AIB-534 | Single query: `status: { in: ['COMPLETED', 'SKIPPED'] }` merging both into one result set | Yes | Simpler, 1 DB query; but conflates COMPLETED and SKIPPED |

**Best**: AIB-535 — Preserves score integrity by keeping COMPLETED scores separate from SKIPPED scans. AIB-534's single query could return a SKIPPED scan as the "latest" and lose the score context.

### Decision Point 2: Score Schema Validation
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-535 | `score: z.number().optional().nullable()`, checks `data.score == null` (covers both null and undefined) | Yes | Robust null handling |
| AIB-534 | `score: z.number().optional()` (no nullable), checks `data.score !== undefined` | Partial | Doesn't handle explicit `null` from agent result |

**Best**: AIB-535 — `.nullable()` correctly handles agents sending `"score": null` in JSON, which AIB-534 would reject as invalid.

### Decision Point 3: Code Reuse (getScoreLabel)
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-535 | Removes duplicate `getScoreDisplayLabel`, uses shared `getScoreLabel` from `score-calculator.ts` | Yes (DRY) | Clean |
| AIB-534 | Keeps local `getScoreDisplayLabel` function | No (duplicate) | Redundant code |

**Best**: AIB-535 — Follows DRY principle by reusing existing utility function.

### Decision Point 4: Workflow SKIPPED Detection
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-535 | Detection inside each scan step (TESTS step, agent step) with per-type defensive guards | Yes | Defensive guards at source; handles edge cases per step |
| AIB-534 | Centralized detection in single consolidation step after scan outputs | Yes | Simpler, single location; checks both `.status` and `.skipped` fields |

**Best**: Tie — Both approaches are valid. AIB-535 is more defensive per-step; AIB-534 is cleaner centralized logic.

### Decision Point 5: State Transitions
| Ticket | Approach | Constitution | Trade-offs |
|--------|----------|--------------|------------|
| AIB-535 | RUNNING → SKIPPED only | Yes | Strict: scan must start before it can be skipped |
| AIB-534 | PENDING → SKIPPED and RUNNING → SKIPPED | Yes | Flexible: allows skipping before scan even starts running |

**Best**: AIB-534 — PENDING → SKIPPED is valid for cases where the workflow detects nothing to evaluate before the agent even starts (saves compute).

## Ranking & Recommendation

### 1. **AIB-535** - Best implementation (score: 88%)
**Why it wins**:
- **Agent command updates**: Only implementation that fulfills FR-012/FR-013 (agent-level "nothing to evaluate" detection)
- **skipReason propagation**: Full-stack propagation of dynamic skip reasons from agent → workflow → API → UI
- **Score schema correctness**: `.nullable()` on score properly handles `null` from agent results
- **DRY code**: Reuses `getScoreLabel` utility instead of duplicating
- **Broader test coverage**: 5 test files including trends exclusion test

### 2. **AIB-534** - (score: 80%)
**Why it scored lower**:
- **Missing agent commands**: Does not update scan agent .md files for early exit — agents won't know to emit SKIPPED
- **No skipReason field**: Hardcoded "Nothing to evaluate" instead of dynamic per-scan-type reasons
- **Score schema gap**: Missing `.nullable()` could reject valid `null` scores from agents

**Where it excels over AIB-535**:
- More comprehensive UI (drawer-history, drawer-states components updated)
- Shows previous score alongside "Skipped" badge (better matches spec Decision 2)
- PENDING → SKIPPED transition support
- Dedicated `health-scan-skipped.test.ts` test suite
